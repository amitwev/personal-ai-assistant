# F10-1 — the writer

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** F9b parsed a `create_task` tool call out of the model's answer but had nothing to do
with it: `ITaskService` had no create method, and `CreateTaskTool` carried no behaviour. F10
closes that gap and, with it, the product's whole capture-to-reminder loop. This slice builds
only the first of F10's three pieces — the writer: `ITaskService.CreateAsync`, and the mapping
extension method that turns a captured request into a `ReminderTask`. Nothing in this slice
touches Telegram, the model, or `CreateTaskTool`. Nothing calls `CreateAsync` from outside a
test after this slice merges. Nothing is supposed to yet.

**Tech Stack:** .NET 10 (`net10.0`), nullable enabled, warnings are errors — the existing stack.
This slice adds **no new NuGet package** and **no database migration** — every column
`CreateAsync` writes (`Title`, `Status`, `DueAt`, `CreatedAt`, `UpdatedAt`) already exists on
`ReminderTask`, and Decision 7, below, is why `Notes` is not one of them.

**Spec:** `docs/design/slice-1-reminders.md` §4.1 (models carry no behaviour), §4.2 (`TaskService`
as the single writer — the interface "grows a method per feature that needs one"), §4.4 (mapping
is extension methods, and specifically the inbound case: "an LLM tool call ... arrives as a
`Contracts` request type, which the service turns into model changes"), §5.1 (capture path flow:
`IAssistantTool -> ITaskService -> repository -> Postgres`), §5.4 (the time contract — resolution
and its guard clauses happen before anything is persisted), §7.2 (unit vs. integration split),
§7.7 (test-driven: failing test, watch it fail, then implement), §12.1 (XML docs), §12.2 (mapping
extension methods, named by destination — its own `ToModel(this CreateTaskRequest request,
DateTimeOffset dueAtUtc)` illustration is this slice's closest spec precedent), §12.5 (primary
constructors), §12.6 (no emoji).
**Backlog:** `docs/design/2026-08-22-slice-1-feature-backlog.md` — F10's own entry (line 597,
"Store the parsed task and reply — observable"), the "Settled at F9b" list immediately above it
(F9b's own deferrals: `ExecuteAsync` arrives at F10 as a deliberate interface modification;
`CreateTaskRequest.DueAtLocal` stays a string, resolved at F10; `Notes` and `Priority` are absent
from the schema, deferred to F10 and F12), and §6 "Order and dependencies" (F8 → F9 → F10 is a
chain; F10 is the milestone "the whole loop works").

## How F10 is sliced

F10's own scope — `ITaskService.CreateAsync`, `IAssistantTool.ExecuteAsync`, binding
`ToolCall.ArgumentsJson` to `CreateTaskRequest`, resolving the local time, and the reply
`MessageHandler` sends in place of its placeholder — splits into three independently reviewable
pull requests, in this order:

- **F10-1 (this plan), the writer** — `ITaskService.CreateAsync` and
  `ReminderTaskMappingExtensions.ToModel`. No tool, no dispatch, no Telegram. **Measured at 120
  lines** (Decision 9, below — drafted in full and counted, not estimated from an analogue).
- **F10-2, the tool executes** — `IAssistantTool.ExecuteAsync` (a modification to an existing
  interface — Decision 3), a new `ToolExecutionResult` contract type, and `CreateTaskTool` gaining
  a primary constructor over `ITaskService` and `ILocalTimeResolver` to actually parse arguments,
  resolve the due time, and call the writer. Tested by resolving `IEnumerable<IAssistantTool>`
  from a real container and calling `ExecuteAsync` directly — the model is not involved, the same
  way F10-1's tests never involve the tool. **Estimated at roughly 250-300 lines**, reasoned from:
  `IAssistantTool.cs` (32 lines today) gaining one member plus a rewritten `<remarks>`, comparable
  in size to `ITaskService.cs` gaining `CompleteAsync` at F6-1 (13 lines) — call it 20; a new
  `ToolExecutionResult.cs` comparable to `ToolCall.cs` (14 lines) with a second, optional property
  — call it 25; `CreateTaskTool.cs` (43 lines, schema-only today) growing a primary constructor and
  an `ExecuteAsync` body comparable in shape to `TaskService.CreateAsync` plus the resolver call —
  call it 90; and a new integration test file exercising the tool directly, comparable in size and
  count to `TaskServiceTests.cs`'s own six tests (156 lines) since this is the same
  "call the service/tool directly, assert business outcomes" shape — call it 140.
- **F10-3, the reply closes the loop · observable** — `MessageHandler` matches `ToolCall.Name`
  against the registered `IEnumerable<IAssistantTool>`, calls `ExecuteAsync`, and replaces the
  `ToolCallNotActedOnYet` placeholder with a real reply carrying the Done button
  (`INotifier.SendTaskAsync`, which already exists and needs no change — F6-3 built it). This is
  the slice that makes F10's own milestone true end to end and is the only one of the three that
  marks the backlog's F10 entry done. **Estimated at roughly 150-200 lines**: `MessageHandler.cs`
  (60 lines today) growing one more branch and one more injected dependency, comparable to its own
  growth from F9a's version to today's `ModelReturnedNoToolCall` branch — call it 50; and
  `TelegramListenerTests.cs` (162 lines today) gaining the full-loop test the backlog names ("call
  the bank tomorrow at 10" ends as a row with a reply carrying the right buttons) plus the
  no-due-time and guard-clause-failure scenarios — call it 130. No fixture work: `WireMockFixture`
  already has `SeedAiToolCallAsync` and `SendMessagePayload.ReplyMarkup` from F9b and F6-3
  respectively, verified by reading the file directly.

**Why this order, and not some other split.** Unlike F6's three slices — which had real freedom in
ordering (the button, the routing, and the writer could technically have shipped in any order; F6
chose button-last specifically to avoid a tap-with-nowhere-to-go hazard) — F10's three pieces have
a strict topological dependency, not merely a risk-managed one. F10-2's `CreateTaskTool` cannot
compile a call to `ITaskService.CreateAsync` until F10-1 adds it. F10-3's `MessageHandler` cannot
compile a call to `IAssistantTool.ExecuteAsync` until F10-2 adds it. There is exactly one buildable
order, and it is the one above. What F10 does share with F6 is the *shape* of the split: each
slice ships a fully working, fully tested layer that nothing outside its own tests calls yet —
F10-1's `CreateAsync` is exercised only by `TaskServiceTests`, the same way F6-1's `CompleteAsync`
was exercised only by `TaskServiceTests` with "no button exists after this slice merges."

**On the 1000-line budget specifically, stated plainly rather than assumed.** Summing the three
estimates above (120 measured + roughly 275 + roughly 175) comes to roughly 570 lines — comfortably
under 1000, and arguably close enough to F9b's own 650-line single-PR precedent that a reviewer
could reasonably ask why this is three pull requests and not one PR in three commits, the way F9b
shipped. This plan does not rest its case on the budget: it rests on the topological-dependency
and working-layer argument above, which holds regardless of the exact byte count. The budget is a
secondary, reinforcing fact — three separately-approvable checkpoints cost nothing extra to
produce, and the F10-2 and F10-3 figures are estimates, not measurements, so treating 570 as a
comfortable margin rather than a hard ceiling is the more honest reading. **This is flagged for
the owner to weigh:** if three pull requests feels like more process than three commits in one PR,
that is a legitimate call to make differently than this plan does, and nothing about F10-1's own
content below changes either way.

## Decisions

### 1. `CreateAsync`'s signature, and why it returns `Result<ReminderTask>` even though it cannot fail

**Decision:**

```csharp
Task<Result<ReminderTask>> CreateAsync(
    CreateTaskRequest request, DateTimeOffset? dueAtUtc, CancellationToken ct);
```

`request` supplies the title (and, later, whatever `CreateTaskRequest` grows — see Decision 7);
`dueAtUtc` is the already-resolved UTC instant, or `null` when the request gave no time.
`CreateAsync` never fails: there is no existing row to find and no precondition comparable to
`MarkReminderSentAsync`'s "no due time" refusal or `CompleteAsync`'s "already completed" refusal.

**Why the whole `CreateTaskRequest` and not just a bare `string title`:** spec §4.4 names this
exact shape — "an LLM tool call ... arrives as a `Contracts` request type, which the service turns
into model changes" — and passing the object `CreateTaskTool` already has (rather than
re-extracting `request.Title` into a scalar) means the day `CreateTaskRequest` gains `Notes` or
another field with a real feature behind it, `CreateAsync`'s signature does not need to change
again; only `ToModel` does. This is the same Open/Closed benefit `MarkReminderSentAsync` and
`CompleteAsync` get from taking a bare `Guid id` — they take exactly what they need and nothing
more, and `CreateAsync`'s "exactly what it needs" happens to be a whole request object because
`CreateTaskRequest` already exists as the vocabulary for this operation.

**Why `dueAtUtc` is a separate parameter, not read off `request.DueAtLocal`:** `TaskService` has no
IANA zone of its own — `ILocalTimeResolver` is the only thing in this codebase that does, and it is
registered as a singleton with no relationship to `TaskService` today. Giving `TaskService` a
resolver dependency just to parse a string it does not otherwise need would pull a whole
capability into the single writer for one field, when the actual owner of "what does this string
mean" is unambiguous elsewhere in the design (Decision 2).

**Why `Result<ReminderTask>` rather than a bare `Task<ReminderTask>`:** every other `ITaskService`
method returns `Result` or `Result<T>`, and a bare `ReminderTask` return would be the one
exception on the interface — a caller pattern-matching on `IsSuccess` elsewhere in this codebase
would need special-case handling for exactly one method. It also costs nothing today and keeps the
door open for a future precondition (a per-user task cap, say) without another signature change —
the same reasoning `docs/tech-debt.md`'s own entries use when they decline to remove `Result`'s
non-generic sibling "on cost grounds" while leaving room for the day a real need arrives.

**Alternative considered and rejected: `CreateAsync(string title, DateTimeOffset? dueAtUtc, CancellationToken ct)`.**
Simpler today, since only `Title` is read. Rejected because it locks the signature to exactly the
fields `CreateTaskRequest` happens to carry right now, so the day `Notes` or `Priority` genuinely
lands (a future feature, per Decision 7), this method's signature would need to grow a third
scalar parameter rather than the mapper alone changing — a wider blast radius for the same future
change, for no benefit today since `CreateTaskTool` already holds a `CreateTaskRequest` and would
otherwise have to unpack it before calling in.

### 2. Where local-time resolution lives: the tool, not the writer

**Decision, taken now because it shapes `CreateAsync`'s own parameter list:** resolving
`CreateTaskRequest.DueAtLocal` against the configured zone, and refusing before anything is
persisted per spec §5.4, happens in F10-2's `CreateTaskTool.ExecuteAsync`, not inside
`TaskService.CreateAsync`. `CreateAsync` receives the outcome — a `DateTimeOffset?` that has
already passed both guard clauses — and never sees the raw string or the resolver at all.

**Why:** F8's own "Settled at F8" note left this genuinely open — "spec §5.4 said a service would
apply them, but F10 is the first feature with a service ... that could even hold them" — a
observation that a service *could* hold the guards, not a decision that it *should*. Putting
resolution in the tool instead keeps `TaskService` a pure persistence boundary: every existing
method on it either finds-and-mutates or, now, builds-and-saves, and none of them interprets
free-form input. `CreateTaskTool` is already the layer translating between the model's world (a
raw JSON string) and the domain's (a bound request), so resolving one more field there — turning a
local-time string into a UTC instant — is the same kind of translation, not a new kind of
responsibility.

**Consequence for this slice:** `TaskService.CreateAsync` needs no `ILocalTimeResolver` dependency
and its primary constructor is unchanged. The two guard-clause `ErrorCode`s
(`DueTimeInPast`/`DueTimeTooFarAhead`) are exercised by F10-2's tests against
`CreateTaskTool.ExecuteAsync` directly, never by this slice's `TaskServiceTests`.

**Alternative considered and rejected: inject `ILocalTimeResolver` into `TaskService` and resolve
inside `CreateAsync`.** Rejected on two grounds. First, it makes `CreateAsync`'s signature take
the raw `CreateTaskRequest.DueAtLocal` string implicitly through `request`, which means a
`Result<ReminderTask>` failure path has to exist after all — contradicting Decision 1's "this
method never fails," and reopening the `ErrorCode` question this slice currently sidesteps
entirely. Second, and more structurally: a caller other than `CreateTaskTool` that already has a
resolved `DateTimeOffset` (there is no such caller yet, but the shape should not preclude one)
would have no way to skip resolution — it would have to fabricate a `DueAtLocal` string just to
have it re-parsed. Keeping resolution one layer up avoids both problems for the cost of one extra
parameter.

### 3. `IAssistantTool.ExecuteAsync`'s exact signature (F10-2, decided now)

Confronted now because it determines what F10-1's `CreateAsync` must be able to hand back, and
because F9b's own Decision 2 already named modifying `IAssistantTool` "the cheapest it will ever
be" while it has exactly one implementation — a cost that only grows once F11 adds three more.
Getting this shape right at F10-2 matters more than it would for an interface F11 will not touch
again.

**Decision:**

```csharp
Task<Result<ToolExecutionResult>> ExecuteAsync(string argumentsJson, CancellationToken ct);
```

with a new `Assistant.Contracts` record:

```csharp
public sealed record ToolExecutionResult(string ReplyText, Guid? TaskId = null);
```

`ReplyText` is what `MessageHandler` sends; `TaskId`, when present, is what lets it attach a
button via `INotifier.SendTaskAsync` instead of a bare `INotifier.SendAsync`. For `create_task`,
`ReplyText` is the new task's title and `TaskId` is its id (Decision 8 gives the exact text). A
future `list_tasks` tool returns a rendered listing with `TaskId: null` — no single task to attach
a button to. A future `complete_task` tool most plausibly also returns `TaskId: null` — the task
already changed state through a different call than a button tap, so there is nothing left to
attach a Done button to.

**Alternative considered and rejected: `Task<Result<ReminderTask>> ExecuteAsync(...)`,** returning
the domain model directly. This is the shape closest to what F10-1 itself returns from
`CreateAsync`, which makes it tempting, but it locks every future tool into producing exactly one
`ReminderTask` — a shape `list_tasks` (many tasks) and `complete_task` (no new entity) cannot fill
without a lie (an empty or duplicate `ReminderTask`) or another interface modification at F11,
which is exactly the compounding cost this decision is trying to avoid by getting the shape right
once.

**Alternative considered and rejected: `Task<Result<string>> ExecuteAsync(...)`,** returning only
reply text. Simpler, and sufficient for a tool that never needs a button. Rejected because
`create_task` does need one today, not hypothetically, and a bare string gives `MessageHandler` no
way to learn which task the reply is about without special-casing `create_task` by name inside the
otherwise-generic dispatcher — precisely the kind of per-tool branching Decision 4's dispatch
design exists to avoid.

**Alternative considered and rejected: `IAssistantTool<TResult>`,** a generic interface parameterised
per tool. Rejected: `AiClient` already depends on `IEnumerable<IAssistantTool>` to build the wire
request (F9b), and a future dispatcher (Decision 4) needs the same homogeneous collection to match
by name and invoke — C# cannot hold `IAssistantTool<CreateTaskRequest>` and a hypothetical
`IAssistantTool<ListTasksRequest>` in one non-generic `IEnumerable`, so this alternative just moves
today's problem one level up without solving it.

### 4. Where tool dispatch lives (F10-3, decided now)

**Decision:** matching `ToolCall.Name` to the right `IAssistantTool` happens inline inside
`MessageHandler`, which already injects `IAiClient` directly (see "Verified facts") and will also
inject `IEnumerable<IAssistantTool> tools`:

```csharp
var tool = tools.FirstOrDefault(t => t.Name == toolCall.Name);
```

No new interface, no `IToolDispatcher`, no new class.

**Why:** this repository already has the identical shape, shipped and tested, for the identical
kind of problem. `CallbackRouter` (F6-2) matches an inbound key against
`IEnumerable<ITaskAction>` the same way: `actions.FirstOrDefault(a => a.Definition.Key ==
actionKey)`, inline, inside the one handler that needs it. Adding a task action at F11 needs no
change to `CallbackRouter`'s matching line — only a new class and one DI registration. The same is
true here: adding `list_tasks`, `update_task`, `complete_task` at F11 needs no change to
`MessageHandler`'s matching line, only new `IAssistantTool` classes and their registrations. This
is Open/Closed at the registration seam, which is where this project has already decided that
seam belongs — not by inventing a second abstraction layer purely for its own sake.

**Alternative considered and rejected: a dedicated `IToolDispatcher`/`ToolDispatcher` class.**
This project has already tried, and reversed, the equivalent move once: F7's own "Settled at F7"
record describes introducing then deleting `OwnerOnlyUpdateHandler`, an abstraction extracted for
a single caller, on the grounds that "an abstraction with one implementation is a guess." A
`ToolDispatcher` today would have exactly one call site (`MessageHandler`) and exactly one
consumer of its output — the same shape. `CallbackRouter` is the living counter-example already in
this codebase: it does not delegate its own matching to an `IActionDispatcher`, it just does the
match. This slice does not touch `MessageHandler` at all, so nothing here is built yet — this
decision is recorded now so F10-3 does not have to re-litigate it.

### 5. What happens when `ILocalTimeResolver.Resolve` fails (F10-2/F10-3 boundary, decided now)

Spec §5.4 requires the caller to turn a failure into a question to the user *before anything is
persisted*. Both codes already exist (F8): `ErrorCode.DueTimeInPast` and
`ErrorCode.DueTimeTooFarAhead`.

**Decision:** `CreateTaskTool.ExecuteAsync` (F10-2) calls `ILocalTimeResolver.Resolve` before
calling `ITaskService.CreateAsync` whenever `CreateTaskRequest.DueAtLocal` is non-null. On failure,
it returns `Result<ToolExecutionResult>.Failure(result.Error!.Value)` immediately —
`ITaskService.CreateAsync` is never called, so nothing is written. `MessageHandler` (F10-3) then
needs two more branches alongside its existing `ModelReturnedNoToolCall` one, mapping each code to
a fixed sentence asking the user to clarify (Decision 8 gives the exact text). The owner sees a
plain question, not an error code and not a stack trace, and can simply answer it as a normal
message — which the existing capture path already treats as a fresh attempt, since there is no
multi-turn state to resume from.

**Why this satisfies "before anything is persisted" structurally, not just by convention:** the
guard runs and can return before `CreateAsync` is ever reached in the call graph — there is no
code path in this design where a resolver failure and a persisted row can both happen for the same
request, because they are sequential steps in one method with an early return between them, not
two independently-triggered side effects that could race or be reordered by a future edit.

**What this slice does with this decision:** nothing directly — `CreateAsync` never sees a resolver
failure at all (Decision 2), so none of `CreateAsync`'s own tests exercise these codes. This
section exists so F10-2's and F10-3's plans do not have to re-derive it, and so the owner can veto
the reply wording (Decision 8) before either slice is built.

### 6. A task with no due time at all

`due_at_local` is optional in `CreateTaskTool`'s schema and `ReminderTask.DueAt` is nullable.

**Decision:** when `CreateTaskRequest.DueAtLocal` is `null`, `CreateTaskTool.ExecuteAsync` (F10-2)
skips the resolver entirely and calls `ITaskService.CreateAsync(request, dueAtUtc: null, ct)`. This
slice's own `ToModel` stores exactly what it is given — `DueAt = null` — and the task is
persisted as `Pending` like any other. It never becomes due: `GetDueRemindersAsync`'s query filters
on `due_at <= @now`, and a `NULL` due date never satisfies that comparison, so the row simply sits
in the table until something else (F11's `update_task`, not this feature) gives it a time.

**What the reply says (forward to F10-3): the same thing it says for a task with a due time** —
the bare title, via `INotifier.SendTaskAsync`, Done button attached. No task in this design is
ever created without at least a title, and the Done button's meaning ("mark this finished") does
not depend on whether a reminder will ever fire for it. This is a deliberate simplicity choice, not
an oversight: an alternative that tells the user explicitly "saved with no reminder" is arguably
more informative and is exactly the kind of thing a reviewer might reasonably push back on — see
the flag on this point in the final report.

### 7. `ReminderTask.Notes` does not ship in this slice, and does not ship anywhere in F10

The backlog's own F10 entry says "`ReminderTask` regains `Notes`, which the capture path is first
to write," and its §4 "Deferred model properties" table repeats it: "`Notes` | Returns at F10."
Applying YAGNI hard, as instructed: **neither is honoured by this plan.**

**Reasoning.** The backlog's own §1 rule is exact: "a feature may only introduce ... a model
property ... that the same feature exercises with a test." The only test scenario F10's own
backlog entry names is "'call the bank tomorrow at 10' ends as a row with the right UTC instant and
a reply carrying the right buttons" — a scenario with no notes content anywhere in it. Tracing
every one of F10's three candidate slices against that same test: F10-1's writer test needs Title
and a resolved due instant, nothing else. F10-2's tool test needs the schema `create_task` already
has today (`title`, `due_at_local`) to bind and resolve, nothing else. F10-3's reply test needs a
task id and a title to render a button, nothing else. No slice's own test, as named, reads or
writes `Notes` anywhere. Under the backlog's own rule, `Notes` therefore does not belong to F10 at
all — it belongs to whichever future feature first writes a test that populates it. Scanning
F11-F14's own backlog entries for such a test: F11's `update_task` parameters (`task_id`, `title?`,
`due_at_local?`, `priority?`) do not include `notes`; F12 is `Priority`; F13 is the raw-capture
fallback and `chat_messages`; F14 is operations. None currently names a `Notes`-exercising test.

**This is reported as a backlog contradiction, not fixed here**, per this task's own instruction:
the backlog commits to `Notes` returning at F10 in two separate places, but nothing in any of
F10's three slices — as the backlog itself scopes them — has a test that needs it. Either a future
plan finds a genuine trigger for it (most plausibly folded into whichever slice first lets the
user add free text beyond a title), or the backlog's two mentions are simply wrong and should be
struck when someone next touches that document. This plan does neither — it just does not add the
column, the migration, or the schema field, and says so here rather than silently matching or
silently ignoring the backlog's claim.

**Consequence for this slice specifically:** no migration, no `ReminderTask` property, no
`CreateTaskRequest` property, no `create_task` schema change. `CreateAsync`'s `request` parameter
carries only what `CreateTaskRequest` already has today (`Title`, `DueAtLocal`) — `DueAtLocal`
itself unread by this method, per Decision 2.

### 8. What the reply text actually is (F10-3, decided now)

Exact strings, so the owner can veto wording before any of F10-2 or F10-3 is built:

| Outcome | Reply text |
| :--- | :--- |
| Captured, with or without a due time | The task's own title, unmodified — sent via `INotifier.SendTaskAsync(task.Id, task.Title, ct)` |
| `ErrorCode.DueTimeInPast` | `"That time has already passed. What time did you mean?"` |
| `ErrorCode.DueTimeTooFarAhead` | `"That is more than two years away, which is probably not what you meant. What time did you mean?"` |

**On a title containing `&`, `<`, or `>`:** nothing new is needed. `INotifier.SendTaskAsync`'s own
contract already says "callers must not pre-escape," and `TelegramNotifier.Escape` — the same
central escaping F7 built to discharge its own HTML debt — runs on every call, this one included.
A title of `"Pay Q&A vendor <urgent>"` is captured, stored, and returned to the caller exactly as
typed; only the outbound Telegram payload carries the escaped form, and that already happens
without any change this slice or its successors need to make.

**Why the capture reply is the bare title, matching `DueReminderJob`'s own reminder text exactly:**
consistency and reuse. The reminder-fired message and the just-captured confirmation now share one
rendering rule — a title, a Done button, nothing else — rather than two different presentations of
the same fact (a pending task) depending on which code path produced the message. The rejected
alternative — echoing back the resolved date and time, e.g. "Call the bank, due tomorrow at
10:00" — is more informative, especially for catching a DST or misread-year edge case before it
becomes a silently-wrong reminder, and is flagged in the final report as a plausible point of
pushback for exactly that reason.
