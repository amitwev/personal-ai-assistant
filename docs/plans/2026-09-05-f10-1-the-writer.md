# F10-1 — the writer

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** F9b parsed a `create_task` tool call out of the model's answer but had nothing to do
with it: `ITaskService` had no create method, and `CreateTaskTool` carried no behaviour. F10
closes that gap and, with it, the product's whole capture-to-reminder loop. This slice builds
only the first of F10's three pieces — the writer: `ITaskService.CreateAsync`, and the mapping
extension method that turns a captured request into a `ReminderTask`. Nothing in this slice
touches Telegram, the model, or `CreateTaskTool`. Nothing calls `CreateAsync` from outside a
test after this slice merges. Nothing is supposed to yet.

**Tech Stack:** .NET 10 (`net10.0`), nullable enabled, warnings are errors — the existing stack.
This slice adds **no new NuGet package** and **no database migration** — every column
`CreateAsync` writes (`Title`, `Status`, `DueAt`, `CreatedAt`, `UpdatedAt`) already exists on
`ReminderTask`, and Decision 7, below, is why `Notes` is not one of them.

**Spec:** `docs/design/slice-1-reminders.md` §4.1 (models carry no behaviour), §4.2 (`TaskService`
as the single writer — the interface "grows a method per feature that needs one"), §4.4 (mapping
is extension methods, and specifically the inbound case: "an LLM tool call ... arrives as a
`Contracts` request type, which the service turns into model changes"), §5.1 (capture path flow:
`IAssistantTool -> ITaskService -> repository -> Postgres`), §5.4 (the time contract — resolution
and its guard clauses happen before anything is persisted), §7.2 (unit vs. integration split),
§7.7 (test-driven: failing test, watch it fail, then implement), §12.1 (XML docs), §12.2 (mapping
extension methods, named by destination — its own `ToModel(this CreateTaskRequest request,
DateTimeOffset dueAtUtc)` illustration is this slice's closest spec precedent), §12.5 (primary
constructors), §12.6 (no emoji).
**Backlog:** `docs/design/2026-08-22-slice-1-feature-backlog.md` — F10's own entry (line 597,
"Store the parsed task and reply — observable"), the "Settled at F9b" list immediately above it
(F9b's own deferrals: `ExecuteAsync` arrives at F10 as a deliberate interface modification;
`CreateTaskRequest.DueAtLocal` stays a string, resolved at F10; `Notes` and `Priority` are absent
from the schema, deferred to F10 and F12), and §6 "Order and dependencies" (F8 → F9 → F10 is a
chain; F10 is the milestone "the whole loop works").

## How F10 is sliced

F10's own scope — `ITaskService.CreateAsync`, `IAssistantTool.ExecuteAsync`, binding
`ToolCall.ArgumentsJson` to `CreateTaskRequest`, resolving the local time, and the reply
`MessageHandler` sends in place of its placeholder, rendered from what was actually persisted —
splits into three independently reviewable pull requests, in this order:

- **F10-1 (this plan), the writer** — `ITaskService.CreateAsync` and
  `ReminderTaskMappingExtensions.ToModel`. No tool, no dispatch, no Telegram. **Measured at 120
  lines** (Decision 9, below — drafted in full and counted, not estimated from an analogue).
- **F10-2, the tool executes** — `IAssistantTool.ExecuteAsync` (a modification to an existing
  interface — Decision 3, overturned by the owner to return `Task<Result<ReminderTask>>` rather
  than a new `ToolExecutionResult` contract type), and `CreateTaskTool` gaining a primary
  constructor over `ITaskService` and `ILocalTimeResolver` to actually parse arguments, resolve the
  due time, and call the writer, handing back the persisted `ReminderTask` itself. Tested by
  resolving `IEnumerable<IAssistantTool>` from a real container and calling `ExecuteAsync` directly
  — the model is not involved, the same way F10-1's tests never involve the tool. **Estimated at
  roughly 225-275 lines** (revised down from an original 250-300 now that no `ToolExecutionResult`
  record is created — see Decision 3), reasoned from: `IAssistantTool.cs` (32 lines today) gaining
  one member plus a rewritten `<remarks>`, comparable in size to `ITaskService.cs` gaining
  `CompleteAsync` at F6-1 (13 lines) — call it 20; `CreateTaskTool.cs` (43 lines, schema-only today)
  growing a primary constructor and an `ExecuteAsync` body comparable in shape to
  `TaskService.CreateAsync` plus the resolver call — call it 90; and a new integration test file
  exercising the tool directly, comparable in size and count to `TaskServiceTests.cs`'s own six
  tests (156 lines) since this is the same "call the service/tool directly, assert business
  outcomes" shape — call it 140.
- **F10-3, the reply closes the loop · observable** — `MessageHandler` matches `ToolCall.Name`
  against the registered `IEnumerable<IAssistantTool>`, calls `ExecuteAsync`, and replaces the
  `ToolCallNotActedOnYet` placeholder with the capture reply Decision 8 now specifies — the title
  and the stored due time rendered back in the configured local zone, or a plain statement that no
  reminder will fire — carrying the Done button (`INotifier.SendTaskAsync`, which already exists
  and needs no change — F6-3 built it; only the `text` argument it is given grows richer). Also
  settles Decision 10, the new sub-decision Ruling E created: rendering `ReminderTask.DueAt` back
  to local text needs a UTC-to-local member this slice adds. This is the slice that makes F10's own
  milestone true end to end and is the only one of the three that marks the backlog's F10 entry
  done — and, per the corrected Decision 7, the one that also corrects the backlog's `Notes`
  mentions. **Estimated at roughly 200-250 lines** (revised up from an original 150-200 now that
  the reply renders a due time rather than a bare title, and Decision 10 adds a small member
  elsewhere): `MessageHandler.cs` (60 lines today) growing two more injected dependencies
  (`IEnumerable<IAssistantTool>` and `ILocalTimeResolver`) and a reply-building branch that renders
  a stored due time or states plainly that none was set, comparable to its own growth from F9a's
  version to today's `ModelReturnedNoToolCall` branch but slightly larger for the formatting call —
  call it 65; `TelegramListenerTests.cs` (162 lines today) gaining the full-loop test the backlog
  names ("call the bank tomorrow at 10" ends as a row with a reply carrying the right buttons and
  the right rendered due time) plus the no-due-time and guard-clause-failure scenarios — call it
  140; and the small addition Decision 10 makes to `ILocalTimeResolver.cs`, `LocalTimeResolver.cs`,
  and two more cases in `LocalTimeResolverTests.cs` — call it 20. No fixture work: `WireMockFixture`
  already has `SeedAiToolCallAsync` and `SendMessagePayload.ReplyMarkup` from F9b and F6-3
  respectively, verified by reading the file directly.

**Why this order, and not some other split.** Unlike F6's three slices — which had real freedom in
ordering (the button, the routing, and the writer could technically have shipped in any order; F6
chose button-last specifically to avoid a tap-with-nowhere-to-go hazard) — F10's three pieces have
a strict topological dependency, not merely a risk-managed one. F10-2's `CreateTaskTool` cannot
compile a call to `ITaskService.CreateAsync` until F10-1 adds it. F10-3's `MessageHandler` cannot
compile a call to `IAssistantTool.ExecuteAsync` until F10-2 adds it. There is exactly one buildable
order, and it is the one above. What F10 does share with F6 is the *shape* of the split: each
slice ships a fully working, fully tested layer that nothing outside its own tests calls yet —
F10-1's `CreateAsync` is exercised only by `TaskServiceTests`, the same way F6-1's `CompleteAsync`
was exercised only by `TaskServiceTests` with "no button exists after this slice merges."

**On the 1000-line budget specifically, stated plainly rather than assumed.** Summing the three
estimates above (120 measured + roughly 250 + roughly 225) comes to roughly 595 lines — comfortably
under 1000, and arguably close enough to F9b's own 650-line single-PR precedent that a reviewer
could reasonably ask why this is three pull requests and not one PR in three commits, the way F9b
shipped. This plan does not rest its case on the budget: it rests on the topological-dependency
and working-layer argument above, which holds regardless of the exact byte count. The budget is a
secondary, reinforcing fact — three separately-approvable checkpoints cost nothing extra to
produce, and the F10-2 and F10-3 figures are estimates, not measurements, so treating 595 as a
comfortable margin rather than a hard ceiling is the more honest reading. **Ruling G — the owner
has confirmed three pull requests**, this plan executing F10-1 only, rather than one PR in three
commits. What this section previously flagged as an open question for the owner to weigh is now
settled: the split stands as designed, and nothing about F10-1's own content below changes either
way.

## Decisions

### 1. `CreateAsync`'s signature, and why it returns `Result<ReminderTask>` even though it cannot fail

**Decision:**

```csharp
Task<Result<ReminderTask>> CreateAsync(
    CreateTaskRequest request, DateTimeOffset? dueAtUtc, CancellationToken ct);
```

`request` supplies the title (and, later, whatever `CreateTaskRequest` grows — see Decision 7);
`dueAtUtc` is the already-resolved UTC instant, or `null` when the request gave no time.
`CreateAsync` never fails: there is no existing row to find and no precondition comparable to
`MarkReminderSentAsync`'s "no due time" refusal or `CompleteAsync`'s "already completed" refusal.

**Why the whole `CreateTaskRequest` and not just a bare `string title`:** spec §4.4 names this
exact shape — "an LLM tool call ... arrives as a `Contracts` request type, which the service turns
into model changes" — and passing the object `CreateTaskTool` already has (rather than
re-extracting `request.Title` into a scalar) means the day `CreateTaskRequest` gains `Notes` or
another field with a real feature behind it, `CreateAsync`'s signature does not need to change
again; only `ToModel` does. This is the same Open/Closed benefit `MarkReminderSentAsync` and
`CompleteAsync` get from taking a bare `Guid id` — they take exactly what they need and nothing
more, and `CreateAsync`'s "exactly what it needs" happens to be a whole request object because
`CreateTaskRequest` already exists as the vocabulary for this operation.

**Why `dueAtUtc` is a separate parameter, not read off `request.DueAtLocal`:** `TaskService` has no
IANA zone of its own — `ILocalTimeResolver` is the only thing in this codebase that does, and it is
registered as a singleton with no relationship to `TaskService` today. Giving `TaskService` a
resolver dependency just to parse a string it does not otherwise need would pull a whole
capability into the single writer for one field, when the actual owner of "what does this string
mean" is unambiguous elsewhere in the design (Decision 2).

**Why `Result<ReminderTask>` rather than a bare `Task<ReminderTask>`:** every other `ITaskService`
method returns `Result` or `Result<T>`, and a bare `ReminderTask` return would be the one
exception on the interface — a caller pattern-matching on `IsSuccess` elsewhere in this codebase
would need special-case handling for exactly one method. It also costs nothing today and keeps the
door open for a future precondition (a per-user task cap, say) without another signature change —
the same reasoning `docs/tech-debt.md`'s own entries use when they decline to remove `Result`'s
non-generic sibling "on cost grounds" while leaving room for the day a real need arrives.

**Alternative considered and rejected: `CreateAsync(string title, DateTimeOffset? dueAtUtc, CancellationToken ct)`.**
Simpler today, since only `Title` is read. Rejected because it locks the signature to exactly the
fields `CreateTaskRequest` happens to carry right now, so the day `Notes` or `Priority` genuinely
lands (a future feature, per Decision 7), this method's signature would need to grow a third
scalar parameter rather than the mapper alone changing — a wider blast radius for the same future
change, for no benefit today since `CreateTaskTool` already holds a `CreateTaskRequest` and would
otherwise have to unpack it before calling in.

### 2. Where local-time resolution lives: the tool, not the writer

**Decision, taken now because it shapes `CreateAsync`'s own parameter list:** resolving
`CreateTaskRequest.DueAtLocal` against the configured zone, and refusing before anything is
persisted per spec §5.4, happens in F10-2's `CreateTaskTool.ExecuteAsync`, not inside
`TaskService.CreateAsync`. `CreateAsync` receives the outcome — a `DateTimeOffset?` that has
already passed both guard clauses — and never sees the raw string or the resolver at all.

**Why:** F8's own "Settled at F8" note left this genuinely open — "spec §5.4 said a service would
apply them, but F10 is the first feature with a service ... that could even hold them" — a
observation that a service *could* hold the guards, not a decision that it *should*. Putting
resolution in the tool instead keeps `TaskService` a pure persistence boundary: every existing
method on it either finds-and-mutates or, now, builds-and-saves, and none of them interprets
free-form input. `CreateTaskTool` is already the layer translating between the model's world (a
raw JSON string) and the domain's (a bound request), so resolving one more field there — turning a
local-time string into a UTC instant — is the same kind of translation, not a new kind of
responsibility.

**Consequence for this slice:** `TaskService.CreateAsync` needs no `ILocalTimeResolver` dependency
and its primary constructor is unchanged. The two guard-clause `ErrorCode`s
(`DueTimeInPast`/`DueTimeTooFarAhead`) are exercised by F10-2's tests against
`CreateTaskTool.ExecuteAsync` directly, never by this slice's `TaskServiceTests`.

**Alternative considered and rejected: inject `ILocalTimeResolver` into `TaskService` and resolve
inside `CreateAsync`.** Rejected on two grounds. First, it makes `CreateAsync`'s signature take
the raw `CreateTaskRequest.DueAtLocal` string implicitly through `request`, which means a
`Result<ReminderTask>` failure path has to exist after all — contradicting Decision 1's "this
method never fails," and reopening the `ErrorCode` question this slice currently sidesteps
entirely. Second, and more structurally: a caller other than `CreateTaskTool` that already has a
resolved `DateTimeOffset` (there is no such caller yet, but the shape should not preclude one)
would have no way to skip resolution — it would have to fabricate a `DueAtLocal` string just to
have it re-parsed. Keeping resolution one layer up avoids both problems for the cost of one extra
parameter.

### 3. `IAssistantTool.ExecuteAsync`'s exact signature (F10-2, decided now) — Ruling A: the owner overturned this plan's own recommendation

Confronted now because it determines what F10-1's `CreateAsync` must be able to hand back, and
because F9b's own Decision 2 already named modifying `IAssistantTool` "the cheapest it will ever
be" while it has exactly one implementation — a cost that only grows once F11 adds three more.
Getting this shape right at F10-2 matters more than it would for an interface F11 will not touch
again.

**Decision, as the owner ruled it:**

```csharp
Task<Result<ReminderTask>> ExecuteAsync(string argumentsJson, CancellationToken ct);
```

No `ToolExecutionResult` record is created.

**This is the owner's call, not this plan's own argument, and the plan adopts it as written.**
This plan's own draft chose a different shape — `Task<Result<ToolExecutionResult>>
ExecuteAsync(...)`, recorded below as the demoted alternative — specifically to avoid locking every
future tool into producing exactly one `ReminderTask`. The owner chose the plainer shape anyway,
while `create_task` is the only tool that exists, and the cost this plan's own argument was built
on is accepted plainly here, not glossed over: a future `list_tasks` (many tasks, not one) and a
future `complete_task` (no new entity to hand back) cannot fill `Result<ReminderTask>` either, so
F11 will have to modify `IAssistantTool` a second time — precisely the compounding cost the demoted
alternative existed to pay once instead of twice. That second modification is now the accepted,
known price of this shape, not a surprise a future plan will have to explain away.

**The reinforcing consequence, and now the strongest argument for this shape.** Because
`ExecuteAsync` hands back the persisted `ReminderTask` itself, whatever renders the capture reply
(Decision 8, rewritten below by Ruling E) reads the row `CreateAsync` actually wrote — title and
due time both — not the model's original arguments and not text `CreateTaskTool` composed before
the write. A misread year or a dropped due time is visible in the reply because the reply is built
from the stored row, not from a paraphrase of the request assembled one layer removed from it. The
`ToolExecutionResult` shape this plan originally chose would have made `CreateTaskTool` responsible
for composing `ReplyText` itself, one step earlier than the actual write — under the shape the
owner chose, there is exactly one renderer (`MessageHandler`, at F10-3) and exactly one source of
truth (the row `CreateAsync` wrote), with no duplicate rendering logic to keep in sync between them.

**Alternative considered and rejected: `Task<Result<string>> ExecuteAsync(...)`,** returning only
reply text. Rejected for the same reason as before, now more clearly: `create_task` needs a
button, and per Decision 8 needs to show the actual persisted due time — a bare string would force
`CreateTaskTool` to duplicate Decision 8's rendering itself, or force `MessageHandler` to
special-case `create_task` by name to reach fields a plain string cannot carry, precisely the kind
of per-tool branching Decision 4's dispatch design exists to avoid. `Result<ReminderTask>` already
carries everything Decision 8's reply needs, with no special-casing.

**Alternative considered and rejected: `IAssistantTool<TResult>`,** a generic interface parameterised
per tool. Rejected: `AiClient` already depends on `IEnumerable<IAssistantTool>` to build the wire
request (F9b), and a future dispatcher (Decision 4) needs the same homogeneous collection to match
by name and invoke — C# cannot hold `IAssistantTool<CreateTaskRequest>` and a hypothetical
`IAssistantTool<ListTasksRequest>` in one non-generic `IEnumerable`, so this alternative just moves
today's problem one level up without solving it.

**Alternative considered, and this plan's own original recommendation — overturned by the owner
(Ruling A):**

```csharp
Task<Result<ToolExecutionResult>> ExecuteAsync(string argumentsJson, CancellationToken ct);
```

with a new `Assistant.Contracts` record:

```csharp
public sealed record ToolExecutionResult(string ReplyText, Guid? TaskId = null);
```

`ReplyText` would have been what `MessageHandler` sends; `TaskId`, when present, would have let it
attach a button via `INotifier.SendTaskAsync` instead of a bare `INotifier.SendAsync`. This plan's
own case for it: it locks nothing about a future `list_tasks` (many tasks) or `complete_task` (no
new entity) into producing exactly one `ReminderTask`, so neither would need to lie with an empty
or duplicate one, and neither would force a second `IAssistantTool` modification at F11. The owner
weighed that case and chose the plainer shape anyway, for as long as `create_task` is the only
tool — see "This is the owner's call," above, for the cost accepted in exchange.

### 4. Where tool dispatch lives (F10-3, decided now)

**Owner-confirmed (Ruling B), exactly as written below — no change to the decision itself.**

**Decision:** matching `ToolCall.Name` to the right `IAssistantTool` happens inline inside
`MessageHandler`, which already injects `IAiClient` directly (see "Verified facts") and will also
inject `IEnumerable<IAssistantTool> tools`:

```csharp
var tool = tools.FirstOrDefault(t => t.Name == toolCall.Name);
```

No new interface, no `IToolDispatcher`, no new class.

**Why:** this repository already has the identical shape, shipped and tested, for the identical
kind of problem. `CallbackRouter` (F6-2) matches an inbound key against
`IEnumerable<ITaskAction>` the same way: `actions.FirstOrDefault(a => a.Definition.Key ==
actionKey)`, inline, inside the one handler that needs it. Adding a task action at F11 needs no
change to `CallbackRouter`'s matching line — only a new class and one DI registration. The same is
true here: adding `list_tasks`, `update_task`, `complete_task` at F11 needs no change to
`MessageHandler`'s matching line, only new `IAssistantTool` classes and their registrations. This
is Open/Closed at the registration seam, which is where this project has already decided that
seam belongs — not by inventing a second abstraction layer purely for its own sake.

**Alternative considered and rejected: a dedicated `IToolDispatcher`/`ToolDispatcher` class.**
This project has already tried, and reversed, the equivalent move once: F7's own "Settled at F7"
record describes introducing then deleting `OwnerOnlyUpdateHandler`, an abstraction extracted for
a single caller, on the grounds that "an abstraction with one implementation is a guess." A
`ToolDispatcher` today would have exactly one call site (`MessageHandler`) and exactly one
consumer of its output — the same shape. `CallbackRouter` is the living counter-example already in
this codebase: it does not delegate its own matching to an `IActionDispatcher`, it just does the
match. This slice does not touch `MessageHandler` at all, so nothing here is built yet — this
decision is recorded now so F10-3 does not have to re-litigate it.

**An open question this decision does not settle, flagged for F10-3.** Matching `ToolCall.Name`
against `tools.FirstOrDefault(t => t.Name == toolCall.Name)` says what happens when the model
names a tool that exists. It does not say what happens when the model names one that does not:
`FirstOrDefault` returns `null`, and no member of today's nine-value `ErrorCode` enum names "the
model asked for a tool this assistant does not have." `create_task` is the only registered tool as
of this slice, so nothing exercises this path yet, and this plan does not invent an answer or an
`ErrorCode` member for it — that is F10-3's decision to make, once it is the slice actually writing
`MessageHandler`'s dispatch branch. A tracking issue for this gap is being opened separately; this
plan only records that the gap exists and names who owns closing it.

### 5. What happens when `ILocalTimeResolver.Resolve` fails (F10-2/F10-3 boundary, decided now)

**Owner-confirmed (Ruling C): both resolver-failure strings below stand verbatim, with no change
to wording.**

Spec §5.4 requires the caller to turn a failure into a question to the user *before anything is
persisted*. Both codes already exist (F8): `ErrorCode.DueTimeInPast` and
`ErrorCode.DueTimeTooFarAhead`.

**Decision:** `CreateTaskTool.ExecuteAsync` (F10-2) calls `ILocalTimeResolver.Resolve` before
calling `ITaskService.CreateAsync` whenever `CreateTaskRequest.DueAtLocal` is non-null. On failure,
it returns `Result<ReminderTask>.Failure(result.Error!.Value)` immediately — `ITaskService.CreateAsync`
is never called, so nothing is written. (The return type follows Ruling A's `ExecuteAsync` shape,
Decision 3 above — not the `ToolExecutionResult` this section originally named before the owner's
ruling.) `MessageHandler` (F10-3) then needs two more branches alongside its existing
`ModelReturnedNoToolCall` one, mapping each code to a fixed sentence asking the user to clarify
(Decision 8 gives the exact text). The owner sees a plain question, not an error code and not a
stack trace, and can simply answer it as a normal message — which the existing capture path
already treats as a fresh attempt, since there is no multi-turn state to resume from.

**Why this satisfies "before anything is persisted" structurally, not just by convention:** the
guard runs and can return before `CreateAsync` is ever reached in the call graph — there is no
code path in this design where a resolver failure and a persisted row can both happen for the same
request, because they are sequential steps in one method with an early return between them, not
two independently-triggered side effects that could race or be reordered by a future edit.

**What this slice does with this decision:** nothing directly — `CreateAsync` never sees a resolver
failure at all (Decision 2), so none of `CreateAsync`'s own tests exercise these codes. This
section exists so F10-2's and F10-3's plans do not have to re-derive it. The reply wording (Decision
8) has now been through the owner's review: the two strings this decision hands off to are
owner-approved verbatim (Ruling C), and the capture-reply wording around them is owner-ruled
(Ruling E) — see Decision 8 for both.

### 6. A task with no due time at all

`due_at_local` is optional in `CreateTaskTool`'s schema and `ReminderTask.DueAt` is nullable.

**Decision, storage half — owner-confirmed (Ruling D):** when `CreateTaskRequest.DueAtLocal` is
`null`, `CreateTaskTool.ExecuteAsync` (F10-2) skips the resolver entirely and calls
`ITaskService.CreateAsync(request, dueAtUtc: null, ct)`. This slice's own `ToModel` stores exactly
what it is given — `DueAt = null` — and the task is persisted as `Pending` like any other. It
never becomes due: `GetDueRemindersAsync`'s query filters on `due_at <= @now`, and a `NULL` due
date never satisfies that comparison, so the row simply sits in the table until something else
(F11's `update_task`, not this feature) gives it a time.

**A consequence the owner has asked to track, not solve here.** An undated task sitting
indefinitely in the table until F11 ships is a real gap, and the owner has asked for a tracking
issue covering it rather than a fix inside this feature. That issue is being opened separately;
this plan records only that the consequence is tracked, not an issue number, and does not invent a
mitigation F10 was never scoped to build.

**What the reply says — overturned by the owner (Ruling E); see Decision 8, rewritten below, for
the exact strings.** This section previously proposed the same reply for a task with a due time
and a task without one — the bare title in both cases — and named the alternative (say plainly
that no reminder will fire) as a plausible point of reviewer pushback rather than adopting it. The
owner adopted exactly that alternative: a task with no due time now gets a reply that says so
plainly, distinct from a task that has one. Decision 8 carries the exact wording and the reasoning
for both cases together, since they are now one decision rather than two independent bare-title
replies that happened to look alike.

### 8. What the reply text actually is (F10-3, decided now) — Ruling E: the owner overturned this plan's own reply design

The owner's words, verbatim: *"i care about what save eventually in the system and to be able to
see it."* The capture reply must show what was actually persisted, not a bare title — for both a
task with a due time and a task without one. This overturns what this plan originally proposed in
Decision 6, above (the bare title, identical for both cases, matching `DueReminderJob`'s own
reminder text). That consistency argument is recorded here as what was traded away, not deleted:
the reminder-fired message and the just-captured confirmation no longer share one rendering rule.
They now say different things, on purpose, because they answer different questions — "here is the
task that is now due" versus "here is exactly what I just saved, so a misread year or a dropped due
time is visible immediately, not after it has already surfaced as a silently wrong reminder."

**Decision — the exact strings:**

| Outcome | Reply text |
| :--- | :--- |
| Captured, with a due time | The task's title, a separator, and the stored due time rendered back in the configured local zone |
| Captured, with no due time | The task's title, a separator, and a plain statement that no reminder will fire |
| `ErrorCode.DueTimeInPast` | `"That time has already passed. What time did you mean?"` |
| `ErrorCode.DueTimeTooFarAhead` | `"That is more than two years away, which is probably not what you meant. What time did you mean?"` |

**The bottom two rows are owner-approved verbatim (Ruling C) and unchanged from this plan's
original wording — see Decision 5.** Only the top two rows change under Ruling E.

**The due-time format, and a worked example of each string.** The due time renders as
`due.ToString("dddd d MMMM yyyy, HH:mm", CultureInfo.InvariantCulture)` — the identical format
string `SystemPrompt.Build()` already uses for "Current time"
(`src/Assistant.Impl/Ai/SystemPrompt.cs`). Reusing it, rather than inventing a second date format,
means every human-facing date this assistant produces reads the same shape, and a reviewer who
checks one format string has checked both. For a task titled "Call the bank" with a due time of 26
August 2026, 10:00 in the configured zone (`Asia/Jerusalem`, a Wednesday):

```
Call the bank -- due Wednesday 26 August 2026, 10:00.
```

For a task titled "Buy milk" with no due time at all:

```
Buy milk -- saved with no reminder.
```

Both are sent via the existing `INotifier.SendTaskAsync(task.Id, text, ct)` — its signature already
takes an arbitrary `text` body (see "Verified facts," above), so nothing about `INotifier` changes;
only the string `MessageHandler` builds and passes to it grows richer. The Done button is attached
in both cases, unchanged: a task with no due time is still a real, completable task, and the
button's meaning ("mark this finished") does not depend on whether a reminder will ever fire for
it.

**Where the due time to render comes from.** `task` here is the `ReminderTask` that `ExecuteAsync`
itself hands back under Ruling A (Decision 3) — the row `CreateAsync` actually wrote, read directly
off `task.DueAt`, not off the model's original `due_at_local` string and not off anything
`CreateTaskTool` composed before the write. This is the reinforcing consequence Decision 3 already
names: the reply is provably the persisted state, not a paraphrase of the request.

**Converting `task.DueAt` (UTC) back to local text is a new sub-decision — see Decision 10,
below.** `ILocalTimeResolver.Resolve` only goes one direction, local to UTC; rendering the stored
value back needed a decision of its own, confronted directly rather than improvised at the call
site.

**On a title containing `&`, `<`, or `>`:** nothing new is needed. `INotifier.SendTaskAsync`'s own
contract already says "callers must not pre-escape," and `TelegramNotifier.Escape` — the same
central escaping F7 built to discharge its own HTML debt — runs on every call, this one included.
A title of `"Pay Q&A vendor <urgent>"` is captured, stored, and returned to the caller exactly as
typed; only the outbound Telegram payload carries the escaped form, and that already happens
without any change this slice or its successors need to make.

**What was traded away, stated plainly.** The bare-title design this plan originally chose bought
one rendering rule shared by the reminder-fired message and the capture confirmation, at the cost
of the confirmation looking identical whether or not a reminder would ever fire, and never showing
the resolved time at all. The owner's ruling spends that shared rule to buy exactly the visibility
this plan itself flagged as the more informative alternative and did not adopt — see Decision 6,
above, for where that flag originally stood.

### 10. Rendering a stored due time back to local text needs a UTC-to-local member (F10-3, decided now) — the sub-decision Ruling E created

Ruling E requires the capture reply to show `task.DueAt` — stored on UTC, per Decision 1 —
rendered back in the configured local zone (Decision 8, above). `ILocalTimeResolver` is verified,
today, to carry exactly three members: `CurrentLocalTime`, `ZoneId`, and `Resolve(DateTime local)`,
which converts local to UTC. None of the three goes the other direction. This is F10-3 work —
nothing in this slice calls `ILocalTimeResolver` at all, per Decision 2 — but the shape of the fix
belongs in this plan, confronted now with the same rigour as every other decision above, not left
for F10-3 to improvise silently.

**Decision:** add a member to `ILocalTimeResolver` — the type that owns the zone. Decision 1,
above, already says so plainly ("`ILocalTimeResolver` is the only thing in this codebase that
[has an IANA zone of its own]"), and Decision 2 relies on that same fact to keep resolution out of
`TaskService`; F9a-2's own decision states the same rule for `ILocalTimeResolver` by name, "the
zone keeps one owner." The member converts a UTC instant to the equivalent wall-clock reading in
the configured zone:

```csharp
DateTimeOffset ToLocal(DateTimeOffset utc);
```

`LocalTimeResolver`'s own implementation already holds the `TimeZoneInfo zone` field this needs —
`CurrentLocalTime` is already exactly `TimeZoneInfo.ConvertTime(timeProvider.GetUtcNow(), zone)` —
so `ToLocal` is a one-line body, `TimeZoneInfo.ConvertTime(utc, zone)`, reusing that same field
rather than adding a second one. Unlike `Resolve`, `ToLocal` returns a bare `DateTimeOffset`, not a
`Result<DateTimeOffset>`: there is no guard clause to apply going from a UTC instant to its local
reading — the "too far in the past" and "too far ahead" business rules exist to catch a
misreading of what the *user* meant when typing a time, not to validate an instant that has
already been resolved and persisted.

**Why this, and not formatting at the render site from the exposed `ZoneId`.** The render-site
alternative would call `TimeZoneInfo.FindSystemTimeZoneById(clock.ZoneId)` and then
`TimeZoneInfo.ConvertTime(dueAtUtc, thatZone)` directly inside whatever builds the reply. This
works, but it duplicates exactly the lookup `LocalTimeResolver` already performs internally to
answer `CurrentLocalTime` — the same zone resolved by string identifier twice, in two different
classes, with nothing enforcing that the two agree. This project has already settled its position
on exactly this question, for exactly this type: F9a-2's own decision states plainly that the zone
keeps one owner, and `ILocalTimeResolver` is that owner — this plan's own Decision 1 and Decision 2
both say so already, for the local-to-UTC direction. A second, independent `TimeZoneInfo` lookup at
a render site would quietly create a second owner for the UTC-to-local direction, one that could
silently drift from the first (a typo in one call's zone string versus the other, say) with nothing
in this codebase positioned to catch it.

**Alternative considered and rejected: format at the render site from `ZoneId`.** Rejected on the
duplication argument above. It also does not save real code: the render site would still need a
`TimeZoneInfo` lookup and a `ConvertTime` call — the same two operations `ToLocal` performs. The
only thing avoided is one interface member and one line of implementation, at the cost of a second
zone-lookup path this codebase has already decided, once, not to have.

**Consequence for this slice:** none directly — `ToLocal` is F10-3's addition to make, to a type
this slice never touches (Decision 2). This decision is recorded now, alongside Decision 8, so
F10-3's own plan does not have to re-derive it or improvise a different answer under time
pressure.
