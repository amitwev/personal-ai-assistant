# Task 3 — Repository, Migrations, and the Integration Test Harness

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to
> implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.
> Test design in §3 MUST be approved by the human before any test is written.

**Goal:** Persist tasks, chat messages, and daily-brief claims in PostgreSQL behind the three
repository interfaces, with a Docker-Compose-backed integration test harness.

**Architecture:** EF Core lives in `Assistant.Repository` and nowhere else. The repositories
implement intent-named queries from `Assistant.Interfaces` and return materialised
`IReadOnlyList<T>`. Postgres comes from `compose.test.yaml`, not Testcontainers; the fixture
owns readiness polling and Respawn-based reset.

**Tech Stack:** EF Core, Npgsql, `dotnet-ef`, xUnit, Respawn, Docker Compose.

**Spec:** `docs/design/slice-1-reminders.md` — §3.2, §4.3, §7.1, §7.2, §9 step 3.
**Parent plan:** `docs/2026-08-16-personal-ai-assistant-slice1-plan.md` — `## Task 3` (line 1683).
**Testing standard:** the `testing-strategy` skill. §3 of this document is written to it.

## 1. Global Constraints

Carried from the parent plan's Global Constraints plus decisions made since.

- `net10.0`; nullable enabled; warnings are errors; `CS1591` is an error in `src/` only.

- Conventional commit messages. Commit at the end of the task.

### 3.2 `TaskRepositoryTests` — SUT `ITaskRepository`

`GetDueRemindersAsync(asOfUtc, limit, ct)` is the method the product depends on. Its predicate has
four independent dimensions, so it is partitioned rather than enumerated.

**Equivalence classes — eligible (task IS returned)**

| # | Scenario | Source |
| :-- | :--- | :--- |
| 1 | due 3 days before `asOfUtc` — no lower bound, so an outage cannot skip it | [SPEC §6.2] |
| 2 | due exactly at `asOfUtc` — **boundary**, predicate is `<=` | [SPEC §6.2] |
| 3 | `DeliveryAttempts` = 2 — **boundary**, one below the cap | [INFERRED] |

**Equivalence classes — ineligible (task is NOT returned)**

| # | Scenario | Source |
| :-- | :--- | :--- |
| 4 | due one second after `asOfUtc` — **boundary**, just outside | [SPEC §6.2] |
| 5 | `DueAt` is null — undated tasks never remind | [SPEC §5.3] |
| 6 | `ReminderSentAt` set — the idempotency key suppresses redelivery | [SPEC §4.3] |
| 7 | status `Completed` | [SPEC §6.2] |
| 8 | status `Cancelled` | [SPEC §6.2] |
| 9 | `DeliveryAttempts` = 3 — **boundary**, at the cap | [SPEC §6.2] |

Implemented as two `[Theory]` tests driven by `MemberData` returning pre-built tasks, so no
branching appears in a test body:

- `GetDueRemindersAsync_EligibleTask_ReturnsTask` — cases 1–3
- `GetDueRemindersAsync_IneligibleTask_ReturnsNoTask` — cases 4–9

**Remaining `[Fact]` tests**

| Test | Asserts | Source |
| :--- | :--- | :--- |
| `GetDueRemindersAsync_MultipleDueTasks_ReturnsOldestFirst` | ordering by `DueAt` ascending | [SPEC §6.2] |
| `GetDueRemindersAsync_MoreDueTasksThanLimit_ReturnsLimitCount` | `LIMIT` honoured | [SPEC §6.2] |
| `AddAsync_TaskWithEveryFieldPopulated_PersistsEveryField` | full round-trip, all columns mapped | [SPEC §4.4] |
| `AddAsync_RowViolatingACheckConstraint_IsRejectedByTheDatabase` `[Theory]` — 3 cases below | the DB refuses, not the app | [SPEC §4.3], [DECISION H] |
| `QueryAsync_TaskWithoutDueTime_ReturnsItAfterDatedTasks` | undated sort last | [INFERRED] |
| `QueryAsync_ByFilter_ReturnsMatchingTasks` `[Theory]` — Overdue / Week / All | filter semantics. **`Today` excluded — see D1** | [INFERRED] |
| `CountOpenWithoutDueDateAsync_PendingTasksWithoutDueTime_ReturnsCount` | count excludes dated and non-pending | [INFERRED] |
| `QueryAsync_UnknownFilter_ThrowsArgumentOutOfRangeException` | an unset filter is refused, never silently treated as `All` | [D2] |

The three constraint cases, supplied by `MemberData`:

| Case | Row | Expected `ConstraintName` |
| :-- | :--- | :--- |
| completed with no completion time | `Status = Completed`, `CompletedAt = null` | `ck_reminder_tasks_completed_consistency` |
| reminder sent with no due time | `ReminderSentAt` set, `DueAt = null` | `ck_reminder_tasks_sent_requires_due` |
| unknown status | `Status = Unknown` | `ck_reminder_tasks_status_known` |

Merged rather than three `[Fact]`s because all three share one setup shape and one assertion
shape — the `test-optimizations` skill's "consolidate negative test cases" (§3).

**Constraint assertions** pin `PostgresException.ConstraintName`, not a substring of a stack
trace. The parent plan does `ex.ToString().ShouldContain("ck_...")`, which passes if the name
appears anywhere in a nested exception chain. Precise form:

```csharp
var ex = await Assert.ThrowsAnyAsync<DbUpdateException>(Act);
var postgres = Assert.IsType<PostgresException>(ex.InnerException);
Assert.Equal("ck_reminder_tasks_completed_consistency", postgres.ConstraintName);
```

### 3.6 Optimization pass — `test-optimizations` skill

Applied to the design above, before anything is written.

**Merges made** (naive one-`[Fact]`-per-scenario would be 25 methods; the design is 13):

| Merged into | From | Strategy |
| :--- | :--- | :--- |
| `GetDueRemindersAsync_EligibleTask_ReturnsTask` `[Theory]` | 3 facts | merge similar (§1) |
| `GetDueRemindersAsync_IneligibleTask_ReturnsNoTask` `[Theory]` | 6 facts | consolidate negatives (§3) |
| `AddAsync_RowViolatingACheckConstraint_IsRejectedByTheDatabase` `[Theory]` | 3 facts | consolidate negatives (§3) |
| `QueryAsync_ByFilter_ReturnsMatchingTasks` `[Theory]` | 3 facts | merge similar (§1) |
| `GetRecentAsync_WindowOfMessages_ReturnsNewestTrimmedOldestFirst` `[Theory]` | 2 facts | merge similar (§1) |

**25 scenarios → 13 test methods, 48% fewer methods, 100% of scenarios preserved.**

**Deliberately NOT merged**, with reasons — the skill's "What NOT to Merge" applies:

- `..._ReturnsOldestFirst` and `..._ReturnsLimitCount` stay separate. They look mergeable (the
  parent plan had them as one test), but they document two distinct requirements. Merged, a
  failure cannot tell you whether ordering or the limit broke. The limit test asserts **count
  only**, so it does not overlap the ordering test's assertion.
- `TryClaimAsync_DateNotYetClaimed_ReturnsTrue` / `..._DateAlreadyClaimed_ReturnsFalse` stay
  separate — "significantly different setup requirements": the second needs a prior claim.
- `AddAsync_TaskWithEveryFieldPopulated_PersistsEveryField` stays alone — a single strict
  full-model comparison, nothing to merge with.

**Two notes where the two testing skills pull against each other:**

1. `testing-strategy` says "single scenario per test"; `test-optimizations` says "remove tests
   fully covered by more comprehensive tests". Where they disagree here — the ordering/limit
   pair — the design keeps them split, because diagnostic precision on failure is worth more
   than one saved method.
2. `test-optimizations` §5 names split test classes `ServiceClassNameTest` (singular) inside a
   `ServiceClassNameTests/` folder, using partial classes. Not adopted: that guidance is for
   classes that have grown too large, and the largest class here holds 8 methods. The design
   instead splits by SUT (one class per repository interface), which achieves the same focus.

The skill's "50-70% reduction" metric is written for optimizing an existing suite. There is no
existing suite here, so it is applied as a design constraint — the count above is measured
against the naive enumeration, not against code that was written and then trimmed.

### 3.7 Conventions every test follows

- xUnit `[Fact]` / `[Theory]`; SUT resolved in the fixture, not per-test `new`.
- AAA with explicit `// Arrange`, `// Act`, `// Assert` comments.
- Gherkin XML summary, `When` / `And` / `Then` each on its own line, business-focused —
  no mention of Respawn, WireMock, or EF.
- `MethodName_Scenario_ExpectedResult` naming.
- Class summary: `/// <summary>Test class for <see cref="ITaskRepository"/>.</summary>` (three-line form).
- Builders named `BuildReminderTask` / `BuildChatMessage` — by type, never `BuildValidX` or `BuildXForY`.
- Literal constants in Arrange; no interpolation, concatenation, loops, or conditionals anywhere
  in a test or a builder.

Example of the target shape:

```csharp
/// <summary>
/// When a task is due three days before the query time
/// And its reminder has not been sent
/// Then it is returned, so an outage cannot silently skip it.
/// </summary>
[Fact]
public async Task GetDueRemindersAsync_DueThreeDaysAgo_ReturnsTask()
{
    // Arrange
    const string title = "Stale";
    var task = BuildReminderTask(title: title, dueAt: Utc("2026-08-14T07:00:00Z"));
    await AddAsync(task);

    // Act
    var result = await GetDueRemindersAsync(Utc("2026-08-17T07:00:00Z"), limit: 50);

    // Assert
    Assert.Equal(title, Assert.Single(result).Title);
}
```

## 4. Decisions — ALL RESOLVED (2026-08-21)

These were the `[INFERRED]` items. The `testing-strategy` skill is explicit that requirements must
not be implied from code, so each was put to the user rather than guessed. All five are now
answered and folded into §3 and §5. **The plan is ready to implement.**

**D1 — RESOLVED: (c) defer to Task 4.**
`TaskFilter.Today` is implemented as `DueAt < asOfUtc.Date.AddDays(1)` — no lower bound (so it
also returns older overdue tasks) and keyed to the **UTC** date, while spec §5.2 says every
user-facing time is Jerusalem local. At 23:00 Jerusalem "today" would run to 03:00 tomorrow.

Consequences now locked in:
- `QueryAsync_ByFilter_ReturnsMatchingTasks` covers **Overdue / Week / All only**. No test pins
  `Today`'s behaviour in Task 3.
- The `TaskFilter.Today` branch in `EfTaskRepository.QueryAsync` still ships as the parent plan
  writes it — untested, and therefore not to be relied on until Task 4.
- **Task 4 owes:** the local-day window using `LocalTimeResolver`, a decision on whether `Today`
  carries a lower bound (i.e. whether it overlaps `Overdue`), and the test for both.

**D2 — RESOLVED: reject it.**
`EfTaskRepository.QueryAsync`'s `switch` currently ends `_ => query`, so `TaskFilter.Unknown`
silently returns every task. Replace that arm with an explicit throw:

```csharp
TaskFilter.All => query,
_ => throw new ArgumentOutOfRangeException(
        nameof(filter), filter, "Filter must be set to a known value."),
```

`ArgumentOutOfRangeException` rather than a swallowed default, because a caller that forgot to set
the filter is a bug at the call site, not a request for everything. Documented by
`QueryAsync_UnknownFilter_ThrowsArgumentOutOfRangeException`, asserted with
`Assert.ThrowsAnyAsync<ArgumentOutOfRangeException>` (never `Assert.Throws<T>`, per Global
Constraints).

**D3 — RESOLVED: confirmed.**
A task with 3 recorded attempts is no longer retried — at most 3 delivery attempts. That is what
`DeliveryAttempts < MaxDeliveryAttempts` (3) implements, and it is now a documented business
requirement rather than an implementation detail. Both sides of the boundary are tested: 2 is
eligible, 3 is not.

**D4 — RESOLVED. Full-model comparison uses `Assert.Equivalent`, which ships with xUnit.**
No external package, no in-house helper. Verified empirically on xunit 2.9.3: it recurses into
nested objects and names the failing member by path (`Mismatched value on member 'Child.Name'`).
`AddAsync_TaskWithEveryFieldPopulated_PersistsEveryField` uses
`Assert.Equivalent(expected, actual, strict: true)` — strict so that a column added later without
a mapping fails the test, which spec §4.4 names as the predictable defect.

One trap this introduces, already reflected in §3: `Assert.Equivalent` compares collections
**order-insensitively** — it passes on `[1,2,3]` vs `[3,2,1]`. Every test in §3 where ordering IS
the requirement (`ReturnsOldestFirst`, `ReturnsNewestTrimmedOldestFirst`,
`ReturnsItAfterDatedTasks`) must therefore use `Assert.Equal` on the projected sequence, never
`Assert.Equivalent`. The `testing-strategy` skill has been updated to carry this warning.

**D5 — RESOLVED: all three stay out of the solution.**
No `.editorconfig`, no `global.json`, no Shouldly. Verified none of the three exists in the repo
today, so this is "never add", not "remove". Concretely for Task 3:
- Parent Step 1's `dotnet add tests/Assistant.IntegrationTests package Shouldly` is **dropped**.
- The parent plan's Task 3 test code is written entirely in Shouldly and must be translated to
  plain xUnit `Assert` as it is transcribed — `ShouldBe` → `Assert.Equal` (expected first),
  `ShouldBeEmpty` → `Assert.Empty`, `ShouldBeNull` → `Assert.Null`,
  `Should.ThrowAsync<T>` → `Assert.ThrowsAnyAsync<T>`.
- Verification step 4 in §6 already greps for any surviving `Shouldly`/`ShouldBe`.
