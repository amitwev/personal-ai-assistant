# F6-1 — the completed column and the writer

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** F6 gives the owner a Done button on a reminder message. Tapping it needs somewhere to
land — a place `ReminderTask` records that it happened, and a service method that writes it
correctly and refuses a repeat write with a name the caller can act on. This slice builds exactly
that and nothing that touches Telegram: `ReminderTask.CompletedAt` returns, its migration and the
`ck_reminder_tasks_completed_consistency` check constraint that keeps it honest, and
`ITaskService.CompleteAsync`, the one place this project's invariant — "`Completed` means
`CompletedAt` is set, and only `Completed` means that" — is enforced. No button exists after this
slice merges. None is supposed to.

**Tech Stack:** .NET 10 (`net10.0`), nullable enabled, warnings are errors — the existing stack.
This slice adds **no new NuGet package**: the migration is generated by `dotnet ef` against
packages `Assistant.Repository` already references, and everything else is plain C#.

**Spec:** `docs/design/slice-1-reminders.md` §4.1 (the full `ReminderTask` shape, `CompletedAt`
included), §4.2 (`ITaskService` as the single writer, and the completion rules Decision 3 below
quotes directly), §6.4 (inline buttons — the effects table names `Done → CompleteAsync`; this
slice ships only the right-hand side), §7.2 (unit vs. integration split), §7.3 (assertion
standard), §7.4 (required scenarios — "Done tapped twice" and "Complete a cancelled task"), §12.1
(XML docs), §12.5 (primary constructors), §12.6 (no emoji). The SQL block at lines 240-264 is
where `ck_completed_consistency`'s predicate is spelled out.
**Backlog:** `docs/design/2026-08-22-slice-1-feature-backlog.md` — F6's own entry (line 274, under
"Reminder path — no AI, no credentials"), and section 4, "Deferred model properties," which
already commits `CompletedAt` to return at F6.

## How F6 is sliced

F6's own diff, all three pull requests summed, is roughly 1100 lines — past this repository's
1000-line budget (backlog §1). It splits into three independently reviewable pull requests, in
this order:

- **F6-1 (this plan), the column and the writer** — `ReminderTask.CompletedAt`, its migration,
  the `ck_reminder_tasks_completed_consistency` check constraint, `ITaskService.CompleteAsync`,
  and its idempotency. No Telegram, no buttons, no callback handling. Roughly 300 lines.
- **F6-2, the tap is routed and answered** — `ITaskAction` and `DoneAction`,
  `ICallbackHandler`/`CallbackRouter` as a second `ITelegramUpdateHandler` for
  `UpdateType.CallbackQuery`, the `v1:<action>:<base64-id>` callback codec, always answering the
  callback query, editing the original message in place, and moving the per-update scope from
  each handler into `TelegramListener.DispatchAsync`, exactly as `docs/tech-debt.md`'s "Each
  handler opens its own scope" entry says F6's own pull request should. Roughly 450 lines.
- **F6-3, the button appears** — a channel-neutral button contract, the `INotifier` surface that
  carries it, `TelegramNotifier` sending `reply_markup`, and `DueReminderJob` attaching a Done
  button to the reminder. Roughly 250 lines.

**Why the button is last, not first.** This is the order Decision 1, below, argues for in full;
the short version is that a button which exists before anything answers its tap does not fail
loudly — it fails as a spinner the owner watches on their phone, because spec §6.4 requires every
callback query to be answered "or Telegram shows a spinner indefinitely." Ordering the machinery
that always answers (F6-2) before the affordance that can be tapped (F6-3) means the button is
visible for the first time only once a tap already has somewhere correct to go. This deliberately
diverges from the backlog's own F6 entry, which lists `ITaskAction`/`DoneAction` before
`ITaskService.CompleteAsync` in its prose — a UI-first reading this plan does not follow.

**A consequence stated plainly:** this slice does not mark the backlog's F6 entry done, and adds
no "Settled at F6-1" list to it. F6 carries the backlog's `observable` tag — demonstrable on a
real phone — and F6-1 alone produces nothing a phone can show. The backlog entry stays open until
F6-3's own plan closes it.

## Decisions

### 1. The button is last, not first

**Decision:** F6 ships as three pull requests in the order named above — the column and the
writer, then the routing and answering machinery, then the visible button — rather than in the
order the backlog's own F6 entry lists its pieces, which reads UI-first (`ITaskAction` +
`DoneAction` named before `ITaskService.CompleteAsync` in that entry's prose).

**Why:** spec §6.4 states three required behaviours for every button action, the first of which
is "Always answer the callback query, or Telegram shows a spinner indefinitely." A button that
exists before anything answers its tap does not fail loudly — it fails as a spinner the owner
watches on their own phone, wondering whether the assistant is still alive. Building the machinery
that always answers (F6-2) before the affordance that can be tapped (F6-3) means the button is
visible for the first time only once a tap already has somewhere correct to go.

**Alternatives considered:**

- **Follow the backlog entry's own listed order (button first).** Rejected: it produces a real,
  tap-shaped hazard the moment the button exists. Shipping the button before `CompleteAsync`
  exists to answer it is not a smaller, safer first step wearing a smaller diff — it is a bigger
  one.
- **Ship all of F6 as one ~1100-line pull request.** Rejected on the 1000-line budget backlog §1
  already sets for every feature in this project — the same ceiling that split F9a into four
  pull requests. 1100 exceeds it regardless of ordering, so a split is required either way; the
  machinery/affordance boundary is the one that keeps each of the three pieces buildable and
  testable on its own, rather than an arbitrary file-count split.

**A consequence worth naming:** the backlog's F6 entry is not marked done by this slice, and gets
no "Settled at F6-1" list of its own — see "What this slice does NOT include," below.

### 2. The check constraint keeps the local `reminder_tasks` prefix

**Decision:** the new constraint is named `ck_reminder_tasks_completed_consistency`, carrying the
same prefix as both constraints already on this table, rather than `ck_completed_consistency`,
the name the spec's own SQL block writes literally (lines 260-261).

**Why:** every check constraint this table has shipped with already carries the prefix —
`ck_reminder_tasks_status_known` and `ck_reminder_tasks_sent_requires_due`
(`ReminderTaskConfiguration.cs:20-23`) — even though the spec's own SQL for both of *those* is
also written unprefixed (`ck_status_known`, `ck_sent_requires_due`, lines 262-264). The
implementation has already silently corrected the spec's naming twice. A third constraint
following the spec's literal text instead of the two it sits beside in the same file would be the
one inconsistent name on the table — an unexplained exception a reader would trip on. The spec's
SQL block reads as illustrative schema, not a literal source of identifiers, the same status this
project has already given it twice over.

**Alternative considered:** name it `ck_completed_consistency`, matching the spec's text exactly.
Rejected — it buys literal spec fidelity at the cost of being the only unprefixed constraint on a
table where the other two are prefixed, for no reader benefit: nothing outside this table's own
configuration file ever references a constraint name by string, so there is no cross-cutting
convention this name needs to match except the one this exact file has already established twice.

### 3. A second tap returns `ErrorCode.TaskAlreadyCompleted`, not success

**Decision:** `CompleteAsync` refuses a second call on an already-completed task with
`Result.Failure(ErrorCode.TaskAlreadyCompleted)`, not `Result.Success()`.

**Why:** spec §6.4 requires, of every button action, that "a second tap on Done yields 'already
done', not an error" — specific wording a caller can only produce if it can tell "just completed
this" apart from "was already completed." `Result` carries no payload (`Result.cs`), so a distinct
`ErrorCode` is the only signal `CompleteAsync` has to hand `DoneAction` (F6-2) that difference.
Returning `Result.Success()` uniformly for both cases is idempotent at the row — no second write
happens either way — but leaves the caller unable to word its reply correctly: it would say
"Marked done" on a tap that changed nothing, rather than "already done" as the spec's own words
quote.

Is an `ErrorCode` the right vehicle for an outcome that is not really a failure? This project has
already made that call once: `ErrorCode.DueTimeMissing` names a completely benign, expected
"there was nothing to do" outcome for `MarkReminderSentAsync`, not a defect. `TaskAlreadyCompleted`
sits in the same place in this design's vocabulary — a refusal with a specific, friendly reason,
not a fault. `Result`'s own doc comment already frames this as "the reason it was refused," not
"the reason something went wrong," so the type's contract already covers this shape without
strain.

**A wording tension worth naming plainly, not glossing over.** Spec §4.2's own bullet list of
`TaskService` rules reads: "Completing an already-completed task is a no-op, so a button can be
tapped twice safely." Read narrowly, "no-op" suggests `Result.Success()` — exactly the alternative
this decision rejects. This plan reads §4.2's "no-op" as describing the *effect* (the row does not
change, nothing new happens, tapping twice is safe) rather than legislating the *mechanism* (which
`Result` factory method reports it), and treats §6.4's specific quoted wording — "already done,"
not a generic success — as the more precise requirement that governs the mechanism.
`TaskAlreadyCompleted` still delivers §4.2's guarantee in full: the second call writes nothing and
changes nothing, proven directly by this slice's own test asserting `CompletedAt` is unchanged.
Commit 2, below, also amends §4.2's sentence to say so precisely, per `AGENTS.md`'s rule that a
structural decision changes the spec in the same commit that makes it.

**Alternative considered and rejected: `Result.Success()` for both cases.** Not a hypothetical —
this project's own abandoned monolith draft did exactly this.
`docs/2026-08-16-personal-ai-assistant-slice1-plan.md` (lines 3689-3707) implemented `CompleteAsync`
with a guard commented "Idempotent on purpose: a button can be pressed twice, and the second press
should read as confirmation rather than as an error," returning `Result.Success()` on the second
call with no distinguishing signal at all — and its own test,
`Completing_twice_succeeds_so_a_button_can_be_pressed_again` (line 3427), asserts exactly that.
Rejected here because it is the shape spec §6.4's specific wording rules out: a caller holding
only `Result.Success()` cannot say "already done" instead of "done." Notably, `ErrorCode.
TaskAlreadyCompleted` already exists as a *name* in that same draft (line 3725) — just attached to
`CancelAsync`, refusing an attempt to cancel a task that is already completed, not to
`CompleteAsync` refusing a repeat of itself. This slice is the first to attach that name to
completion's own idempotency; the name is not new to this project's vocabulary, only this
particular use of it is.

### 4. A `Cancelled` task is out of scope

**Decision:** `CompleteAsync` has no branch for `ReminderStatus.Cancelled` in this slice. Not a
silent omission — stated outright, here.

**Why it is safe to omit:** no feature in the current backlog (F1 through F14) ever sets
`ReminderStatus.Cancelled`. The closest is F11 ("Snooze and reschedule," spec §6.4, §4.2), which
moves `DueAt` and clears `ReminderSentAt`, and never touches `Status`. Slice 1 *defines* the value
(`ReminderStatus.Cancelled = 3`) but nothing in the planned F1-F14 sequence produces it. A branch
guarding a state nothing can reach is exactly what backlog §1's definition of done forbids: "no
code was added that nothing exercises."

**The tension with spec §7.4, named rather than hidden:** the required-scenarios table lists
"Complete a cancelled task | Rejected" as a scenario this feature must eventually satisfy. It is
on that list, and it is unreachable today — both true at once. It is deferred, not dropped: the
row stays in the spec as a marker for whichever future feature introduces a cancel path, and this
slice does not claim to satisfy it.

**What would change if a cancel path ever arrives:** the abandoned monolith draft already sketches
the shape (`CancelAsync` at lines 3715-3731, and `CompleteAsync`'s own `Cancelled` guard at lines
3697-3700). `CompleteAsync` would gain a branch checking `task.Status == ReminderStatus.Cancelled`
— ordered before the `Completed` check, since a task cannot be both — returning a new `ErrorCode`
(the draft calls it `TaskCancelled`) rather than reusing `TaskAlreadyCompleted`, which this
slice's Decision 3 has already committed to meaning specifically "was completed, not cancelled."
Whichever feature adds `CancelAsync` owns that branch and that enum member; this slice adds
neither.

### 5. `CompleteAsync` sets nothing beyond `Status`, `CompletedAt` and `UpdatedAt`

**Decision:** `CompleteAsync` touches exactly three fields and leaves `ReminderSentAt` and
`DueAt` untouched.

**Why this is sufficient, verified against the two places that decide what counts as due:**

- The partial index `idx_tasks_due_pending` filters on `status = 1 AND reminder_sent_at IS NULL`
  (`ReminderTaskConfiguration.cs:37-39`). Status `1` is `Pending`; once `CompleteAsync` sets
  `Status` to `Completed` (`2`), the row falls outside the index's filter regardless of what
  `ReminderSentAt` or `DueAt` still hold.
- `EfTaskRepository.GetDueRemindersAsync` filters `t.Status == ReminderStatus.Pending` directly
  in its `Where` clause (`EfTaskRepository.cs:37-39`) — not "not completed," `Pending`
  specifically — so the same status change excludes the row from the query the scheduler actually
  runs, independent of the index.

Both guards key on `Status` alone. Clearing `ReminderSentAt` or `DueAt` on completion would only
matter if some later code path re-read them after completion expecting a particular value, and
nothing does: `GetDueRemindersAsync` never returns a completed task to any caller, so
`MarkReminderSentAsync` is never invoked on one either.

**Alternative considered: also clear `ReminderSentAt` back to `null`, "for cleanliness."**
Rejected — it changes a field slice 1's own semantics document (§4.1) defines as "when the
reminder for the current `DueAt` was delivered." Clearing it on a task that is now finished would
misrepresent history (the reminder for that due time genuinely was delivered, or genuinely was
not) for no read path that consumes it after completion. Touching a field with no consumer is the
same YAGNI violation backlog §1 already rules out for new code; it applies equally to an
unnecessary write on an existing one.

```csharp
    /// <inheritdoc/>
    public async Task<Result> CompleteAsync(Guid id, CancellationToken ct)
    {
        var task = await repository.FindAsync(id, ct);

        if (task is null)
        {
            return Result.Failure(ErrorCode.TaskNotFound);
        }

        if (task.Status == ReminderStatus.Completed)
        {
            return Result.Failure(ErrorCode.TaskAlreadyCompleted);
        }

        var now = timeProvider.GetUtcNow();

        task.Status = ReminderStatus.Completed;
        task.CompletedAt = now;
        task.UpdatedAt = now;
        await repository.UpdateAsync(task, ct);

        return Result.Success();
    }
```

`using`. No constructor change: `repository` and `timeProvider` are the same two primary
constructor parameters `MarkReminderSentAsync` already uses.
