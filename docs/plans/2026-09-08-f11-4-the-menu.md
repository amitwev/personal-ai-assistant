# F11-4 — the menu

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** F11-1 (`8989d6c`), F11-2 (`cc8f82d`), and F11-3 (`773132e`) built `RescheduleAsync`,
`CallbackCodec`'s fourth segment, `ITaskAction`'s widened shape, `TaskActions.Schedule` and
`ScheduleAction`, and the two-button `[Done] [+1h]` keyboard `CallbackRouter` now renders by the
task's own `Status`. F11-4 is meant to be F11's fourth and final pull request: `Schedule` becomes a
menu opener, and `+3h`, `Tonight 20:00`, `Tomorrow 09:00`, and `Back` join `+1h` as presets inside
it. **Measuring the real diff during this planning session found that shipping all of that in one
pull request lands at roughly 1050-1100 changed lines, over the project's 1000-line budget** — see
Decision 1. This plan therefore builds **F11-4a**: a second registration seam, `ITaskNavigation`,
parallel to `ITaskAction`; the schedule menu itself; and a `Back` button, carrying forward only the
existing `+1h` preset. **F11-4b** — `+3h`, `Tonight 20:00`, `Tomorrow 09:00`, and the
`ILocalTimeResolver` work the two wall-clock presets need — is deferred to a fifth pull request,
described but not built here. F11 stays open until F11-4b lands.

After this slice merges, the owner can tap `Schedule` on a real task message, watch the keyboard
swap to `[+1h] [Back]` with the message text unchanged, tap `Back` to return to `[Done] [Schedule]`
with the task still untouched, or tap `+1h` to reschedule and watch the keyboard return to
`[Done] [Schedule]` on its own.

**Tech Stack:** `net10.0`, nullable enabled, warnings are errors — the existing stack. This slice
adds **no new NuGet package** and **no database migration**: nothing about `reminder_tasks`
changes, and swapping a keyboard needs no new dependency.

**Spec:** `docs/design/slice-1-reminders.md` §6.4 (inline buttons — corrected here: the button
table splits into a main-keyboard table and a schedule-menu table, and the byte-budget sentence is
replaced with the real computed number) and §4.2 (`TaskService` as single writer — read, not
touched: nothing here mutates a task). §7.2 (unit vs. integration split), §7.3 (assertion

**Backlog:** `docs/design/2026-08-22-slice-1-feature-backlog.md` — the F11 entry is corrected here

### 2. `ITaskNavigation` is a second registration seam, parallel to `ITaskAction`

**Decision:**

```csharp
public interface ITaskNavigation
{
    TaskNavigationDefinition Definition { get; }
}
```

with a parallel `Assistant.Contracts` catalogue mirroring `TaskActions`'s own shape: an enum
`TaskKeyboard { Unknown, Actions, ScheduleMenu }`; a record `TaskNavigationDefinition(string Key,
string Label, TaskKeyboard Shows, string Description)`; and a static `TaskNavigations` class with
`OpenSchedule` (key `menu`, shows `ScheduleMenu`), `Back` (key `back`, shows `Actions`), and `All`
— full code in "Steps."

`CallbackRouter` takes `IEnumerable<ITaskNavigation> navigations` alongside its existing
`IEnumerable<ITaskAction> actions`, and matches an inbound key against it exactly the way it
already matches `actions` — the identical registration-seam shape `MessageHandler` already uses
for `IEnumerable<IAssistantTool>`.

**The rejected alternative, and why F11-3 already forced this choice.** F11-3's Decision 6 named
and rejected "a switch on the action's own key" inside `CallbackRouter` — `actionKey == "done" ?
... : ...` — as the wrong shape for exactly the coupling reason this slice would otherwise
reintroduce: it makes the router the one place that must know the complete, current roster of
every button that will ever exist. Naming `menu` and `back` directly inside `CallbackRouter`'s
body — `if (actionKey == "menu") { ... } else if (actionKey == "back") { ... }` — is that same
rejected shape, just for navigation instead of action. F11-3's own central decision was that the
router names no action by key; a navigation-specific carve-out inside the router would spend that
decision's whole point the very next slice that touched it.

**The one real objection, stated rather than buried.** `ITaskNavigation` has exactly one member, a
property, and no method — it does no work of its own. Compare `ITaskAction.ExecuteAsync`, which
returns `Task<Result<ReminderTask>>` and is where the actual behaviour lives; `ITaskNavigation`
has nothing analogous. This makes it, honestly, a marker for the DI seam rather than a contract for
behaviour — a thinner interface than `ITaskAction`'s own precedent might suggest is warranted for a
second one.

**Why that thinness is still the right call here, not a smell to fix.** The behaviour a navigation
performs — attach a different keyboard, change nothing else — is not per-navigation; it is the
same one line for every navigation that will ever exist:
`notifier.ShowKeyboardAsync(messageId, taskId, messageText, navigation.Definition.Shows, ct)`. A
method on `ITaskNavigation` would have to either do exactly that (identical boilerplate in every
implementation) or diverge, breaking the invariant that makes the router's dispatch safe: every
navigation only ever swaps a keyboard. The value this interface buys is not behaviour polymorphism
— it is registration polymorphism: a future navigation is a class plus one `AddScoped` line, never
an edit to `CallbackRouter`. The simpler alternative — no interface, `TaskNavigations.All` matched
against a hardcoded `Dictionary<string, TaskKeyboard>` inside the router — was considered and
rejected for the same reason F11-3 rejected the inline switch: it works with exactly two
navigations and stops working the moment a third needs anything the dictionary does not already
express.

### 3. The button roles, as of this slice

**Decision:** Main keyboard: `[Done] [Schedule]`. `Done` stays `TaskActions.Done`, unchanged.
`Schedule` is now `TaskNavigations.OpenSchedule` — key `menu`, label `Schedule`, shows
`TaskKeyboard.ScheduleMenu` — not an action tap. Schedule menu: `[+1h] [Back]`. `+1h` is
`TaskActions.Schedule` carrying `ScheduleAction.PlusOneHour`, exactly as F11-3 built it, moved from
the main keyboard into the menu. `Back` is `TaskNavigations.Back` — key `back`, label `Back`, shows
`TaskKeyboard.Actions`.

**After `+1h` is tapped, the menu closes by itself — say this explicitly, because it is why no
"close the menu" action is needed.** A successful `+1h` tap changes the task's `DueAt`, so
`CallbackRouter`'s existing status-based render path runs (F11-3 Decision 6, untouched by this
slice) and calls `notifier.UpdateTaskAsync(...)`. `UpdateTaskAsync` always attaches
`TaskKeyboard.Actions` — it always did, even before this slice, since it always rendered the one
keyboard that existed. The only change this slice makes to that path is that `Actions` is now one
of two possible keyboards rather than the only one; which keyboard was showing when the tap
happened is never read. A `+1h` tap made from inside the menu therefore returns to the main
keyboard automatically, with no branch anywhere asking "was a menu open."

**F11-4b's own menu is `[+1h] [+3h] [Tonight 20:00] [Tomorrow 09:00] [Back]`** — previewed in
Decision 7, not built here.

### 4. `TaskActions.Schedule.Label` stays `"+1h"` — the dangling remark is resolved, not left

**Decision:** `TaskActions.Schedule.Label` is unchanged: still the literal string `"+1h"`. Its
`<remarks>` are rewritten:

```csharp
/// <summary>
/// The schedule menu's one preset button today.
/// </summary>
/// <remarks>
/// The label is still "+1h": that is still the only preset <c>ScheduleAction</c> recognises,
/// and "+1h" is still the exact text a tap on this button applies -- only its position moved,
/// from the main keyboard into the schedule menu <see cref="TaskNavigations.OpenSchedule"/>
/// now opens. The main keyboard's own Schedule-labelled button is that navigation, not this
/// action -- see <see cref="TaskNavigations"/>. Once a second preset is registered, each one
/// will carry its own label from a dedicated catalogue, and this field's role will need a
/// second look then.
/// </remarks>
public static TaskActionDefinition Schedule { get; } = new(...);
```

**Why this is a real resolution, not a deferral wearing a different sentence.** F11-3's own text
made a forward-looking claim — "F11-4 renames it once tapping the button opens a menu instead of
applying one preset" — that this slice is now obligated to make true or correct. The claim was
wrong on the premise: opening a menu did not require renaming this label, because `Schedule` (the
action) and `Schedule` (the new navigation, coincidentally sharing a display word) are two
different catalogue entries now, and only the navigation's label was ever going to say `"Schedule"`
to a human. `TaskActionDefinition.Label`'s own contract — "the text a human reads on the button
itself" — is still exactly true of `+1h`, still rendered verbatim by `BuildScheduleMenuKeyboard`.
Nothing about that contract broke; only the sentence claiming it would need to was wrong.

**Why this is *not* the moment to touch `TaskActionDefinition.Label`'s own doc.** The brief that
produced this plan anticipated a harder version of this question — how one `Label` field serves an
action offered through *several* preset buttons, each needing its own text — and that question is
real, but it is F11-4b's: F11-4a never gives `ScheduleAction` a second preset, so `Label` is never
asked to speak for more than one button here. Answering it now, before a second preset exists to
make the answer checkable by anything other than reading the code, would repeat the mistake F11-2's
own Decision 5 named and declined for `ToMessageText`: building a seam before the second caller
that could prove it correct. The corrected `<remarks>` above name the trigger — "once a second
preset is registered" — rather than attempting the answer early.

### 5. `INotifier.ShowKeyboardAsync`: a third, distinct edit method — and why the two keyboard
   builders stay hand-built at today's size

**Decision:**

```csharp
Task ShowKeyboardAsync(int messageId, Guid taskId, string text, TaskKeyboard keyboard, CancellationToken ct);
```

implemented by routing every keyboard `TelegramNotifier` ever sends through one dispatcher:

```csharp
private static InlineKeyboardMarkup BuildKeyboard(Guid taskId, TaskKeyboard keyboard) => keyboard switch
{
    TaskKeyboard.Actions => BuildActionsKeyboard(taskId),
    TaskKeyboard.ScheduleMenu => BuildScheduleMenuKeyboard(taskId),
    _ => throw new ArgumentOutOfRangeException(nameof(keyboard), keyboard, "Unrecognised TaskKeyboard value."),
};
```

`SendTaskAsync` and `UpdateTaskAsync` both now call `BuildKeyboard(taskId, TaskKeyboard.Actions)`
in place of the old `BuildTaskKeyboard(taskId)`; `ShowKeyboardAsync` calls
`BuildKeyboard(taskId, keyboard)` with whatever `CallbackRouter` passed it.

**Why a fourth `INotifier` method, not a `TaskKeyboard` parameter bolted onto `UpdateTaskAsync`.**
The identical reasoning F11-3's Decision 4 used for `UpdateTaskAsync` itself: the two edits have
opposite contracts. `UpdateTaskAsync` means "the task changed; rebuild the text, and always show
the main keyboard, since whatever menu was open is now stale." `ShowKeyboardAsync` is the opposite
in both particulars: the task did *not* change, so the text is preserved verbatim, and the keyboard
is exactly the caller's choice rather than always `Actions`. One method with a `TaskKeyboard`
parameter defaulting to `Actions` would make every call site's meaning depend on which argument it
happened to pass, where two names read at the call site with no need to open the implementation.

**Why the two keyboard-building methods stay hand-built, not a loop over a catalogue, at this
slice's size.** F11-3's Decision 5 built one two-button row by hand and deferred the
loop-versus-hand-build question to "once `Schedule` becomes a variable-width row of presets." That
trigger has not arrived: `BuildScheduleMenuKeyboard` renders exactly two buttons — `+1h` and
`Back` — a fixed width, same as `BuildActionsKeyboard`'s `Done` and `Schedule`. A loop over
`SchedulePresets.All` would be machinery for a plurality this slice does not have; that catalogue
does not exist until F11-4b. The comment left on `BuildKeyboard` names the one method F11-4b will
need to change.

### 6. `CallbackRouter`'s navigation branch: where it sits, the too-old-message guard's extension,
   and why it names no key literal

**Decision:** The navigation lookup sits inside the existing "no action matched" branch, tried only
after every registered `ITaskAction`'s key has already failed to match:

```csharp
var action = actions.FirstOrDefault(a => a.Definition.Key == actionKey);

if (action is null)
{
    var navigation = navigations.FirstOrDefault(n => n.Definition.Key == actionKey);

    if (navigation is not null)
    {
        if (messageText is not null)
        {
            await notifier.ShowKeyboardAsync(messageId, taskId, messageText, navigation.Definition.Shows, ct);
        }

        await bot.AnswerCallbackQuery(callbackQueryId, cancellationToken: ct);
        return;
    }

    await bot.AnswerCallbackQuery(callbackQueryId, ThatButtonIsNoLongerValid, cancellationToken: ct);
    return;
}

var result = await action.ExecuteAsync(taskId, argument, ct);
// ... unchanged from F11-3 ...
```

**Why this placement, not a lookup tried first, or the two merged into one collection.** Actions
and navigations use disjoint keys by construction — `done`/`schedule` against `menu`/`back` — so
trying actions first costs nothing on every navigation tap: one `FirstOrDefault` finding nothing,
then a second lookup that succeeds. `TaskNavigationsTests` (new, this slice) asserts the
disjointness directly, so a future collision is caught by a fast unit test rather than a navigation
silently becoming unreachable. This ordering is also the smallest possible diff against
`CallbackRouter.cs`'s existing shape: the pre-existing action-matching block is untouched, and the
navigation branch is inserted as new lines inside the one branch that used to do nothing but answer
"not valid." Merging the two into one `IEnumerable<object>` keyed lookup was considered and
rejected: `ITaskAction` and `ITaskNavigation` share no common member beyond `Key`, so the merge
would need a wrapper type carrying nothing — machinery to save four lines that would cost readers
the ability to tell, at the call site, which kind of thing was found. The router still names no key
literal in its own body: it reads `navigation.Definition.Shows` to decide which keyboard to
attach, never `"menu"` or `"back"` anywhere in the file — F11-3's central decision, carried forward
rather than reopened.

**The too-old-message guard now protects two calls, not one, and the reasoning is the same reasoning
F11-3 already used to decide which calls it protects.** `messageText is not null` wraps
`MarkCompletedTaskAsync` (needs the prior text to strike through) and now also
`ShowKeyboardAsync` (needs it to preserve verbatim — there is nowhere else for a navigation to read
text from, since it never touches a task and so never has a fresh `ToMessageText` to rebuild from).
It still does not wrap `UpdateTaskAsync`, which builds its text fresh from the task and runs
unconditionally, exactly as F11-3 left it. `Listener_NavigationTappedOnATooOldMessage_...` is the
new assertion proving the guard's extension, not merely stating it.

### 8. The open product question for F11-4b — recommend surfacing the refusal as a toast

**The question, argued now even though the code is F11-4b's.** `Tonight 20:00` tapped at 21:00
local names a time that has already passed. "Verified facts" already establishes what
`ILocalTimeResolver.Resolve`'s past-time guard actually does: it refuses with
`ErrorCode.DueTimeInPast` whenever the resolved instant is more than a minute before the current
one — not a clamp, not a silent adjustment, a refusal exactly like any other `Resolve` failure this
codebase already handles (`CreateTaskTool` already surfaces the identical error code for the same
reason, from the LLM capture path).

**Three options, laid out rather than picked without argument:**

(a) **Surface the refusal as a callback answer** — a short toast reading something like "That time
    has already passed." — and change nothing else. `ScheduleAction`'s `Result<ReminderTask>`
    already carries `ErrorCode.DueTimeInPast` up to `CallbackRouter` unchanged; the only new code
    is one more arm in the existing reply `switch`.

(b) **Silently roll `tonight` to tomorrow evening** when today's 20:00 has already gone by.

(c) **Hide or disable the button after 20:00**, so the tap is never possible in the first place.

**Recommendation: (a).** (b) makes a button labelled `Tonight 20:00` silently do something its own
label denies — tapping it at 21:00 would set a reminder for *tomorrow* evening while the button
still reads `Tonight`. That is the identical overpromising-label objection F11-3's Decision 1 used
to reject labelling the main-keyboard button `Schedule` before a menu existed to make that word
true: a label must say what tapping it does right now, not what the code has quietly reinterpreted
it into. (c) means the keyboard a message shows depends on the wall-clock instant it happens to be
rendered at — the same task showing a four-button menu at 19:00 and a three-button one at 20:01 —
making `TelegramNotifier`'s output a function of *when* it runs, and needing `TimeProvider` or
`ILocalTimeResolver` threaded into keyboard-building code that has needed neither so far. (a) keeps
the menu a pure function of the task, and treats a refused preset exactly as
`Listener_ScheduleTappedWithAnUnrecognisedArgument_...` already treats an unrecognised one — a
toast, no edit, the task unchanged.

**This is marked explicitly as a decision the reviewer should confirm before F11-4b is planned in
earnest** — it is a product call about what the owner sees on their own phone, not purely an
engineering one, and this plan's recommendation is exactly that: a recommendation, not a fait
accompli.
