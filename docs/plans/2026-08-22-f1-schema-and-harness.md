# F1 — Database schema and the integration test harness

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** A real PostgreSQL database with the `reminder_tasks` table, its check constraints, and
an integration test harness that proves both — with no repository methods.

**Architecture:** EF Core lives only in `Assistant.Repository`. The context and its configuration
are internal; the assembly's public surface is `AddAssistantRepository` and (later) the
repositories. Postgres comes from `compose.test.yaml`, not Testcontainers; the fixture owns
readiness polling and Respawn reset.

**Tech Stack:** EF Core 10.0.11, Npgsql provider 10.0.3, `dotnet-ef` 10.0.11 (global), xUnit,
Respawn, Docker Compose.

**Spec:** `docs/design/slice-1-reminders.md` §3.2, §4.3, §7.1.
**Backlog:** `docs/design/2026-08-22-slice-1-feature-backlog.md` — F1.

---

## Global Constraints

- `net10.0`; nullable enabled; warnings are errors; `CS1591` is an error in `src/` only.
- **EF Core types appear only in `Assistant.Repository`.** `Impl` never references `Repository`.
- All instants UTC. `DateTimeOffset` **must** have `Offset == TimeSpan.Zero` — Npgsql throws on
  `timestamptz` otherwise.
- Plain xUnit `Assert`. No Shouldly, no FluentAssertions. `Assert.Equal(expected, actual)` —
  expected first. `Assert.ThrowsAny<T>` / `ThrowsAnyAsync<T>`, never `Assert.Throws<T>`.
- Every `<summary>` is three lines: open tag, text, close tag.
- Central package management is on: a `PackageReference` with an inline `Version=` is an error
  (NU1008). Versions go in `Directory.Packages.props`.
- No `.editorconfig`, no `global.json`, no `.config/dotnet-tools.json`. `dotnet-ef` is global
  and already at 10.0.11.
- **YAGNI:** this feature introduces nothing it does not test.
- PR budget: 1000 lines. Estimated ~450, of which ~300 is generated migration code.

## What F1 does NOT include, and why

| Excluded | Returns at |
| :--- | :--- |
| Any `ITaskRepository` implementation | F2 — `AddAsync`/`FindAsync` |
| `idx_tasks_due_pending` partial index | F3 — it exists to serve `GetDueRemindersAsync`, and F1 cannot exercise it |
| `ck_completed_consistency` | F6 — needs the `completed_at` column, which returns with the Done button |
| `notes`, `priority`, `delivery_attempts`, `completed_at` columns | F10, F12, F11, F6 |
| `chat_messages`, `daily_brief_log` tables | F13, F12 |

**The table therefore has 7 columns, not 11**, matching `ReminderTask`'s 7 properties. Spec §4.3
shows the finished schema; F1 builds the part that exists today.

### Task 2: The context, the configuration, and the migration

**Files:** create `AssistantDbContext.cs`, `Configurations/ReminderTaskConfiguration.cs`,
`RepositoryServiceCollectionExtensions.cs`, `Migrations/`.

- [ ] **Step 1: Write `AssistantDbContext`**

Internal, sealed. One `DbSet<ReminderTask> ReminderTasks`. `OnModelCreating` applies
configurations from the assembly. Internal members need no XML docs, but write them anyway on
anything public.

- [ ] **Step 2: Write `ReminderTaskConfiguration`**

Internal sealed `IEntityTypeConfiguration<ReminderTask>`. Table `reminder_tasks`, snake_case
columns, `Status` via `HasConversion<int>()`, all `DateTimeOffset` as `timestamptz`,
`Title` required with `HasMaxLength(500)`.

Two check constraints — and **only** these two:

```csharp
t.HasCheckConstraint("ck_reminder_tasks_status_known", "status <> 0");
t.HasCheckConstraint("ck_reminder_tasks_sent_requires_due",
    "reminder_sent_at IS NULL OR due_at IS NOT NULL");
```

`ck_completed_consistency` is **not** added — it references `completed_at`, which does not exist
until F6. Adding it now would fail to compile into valid SQL.

No index. `idx_tasks_due_pending` belongs to F3, with the query it serves.

- [ ] **Step 3: Write `RepositoryServiceCollectionExtensions`**

Public static class, the assembly's only public surface. `AddAssistantRepository` registers
`AssistantDbContext` with `UseNpgsql(connectionString)`. `MigrateAssistantDatabaseAsync`
resolves the context in a scope and calls `Database.MigrateAsync()`.

Migrations are applied by an explicit call rather than inside `AddAssistantRepository`: the
fixture needs to migrate once per run, and hiding a schema mutation inside a DI registration
makes it impossible to control. Spec §8 says migrations apply at startup; F14 wires that call
into `Program.cs`.

XML docs on both methods, three-line summaries.

- [ ] **Step 4: Add a design-time context factory**

`dotnet ef` builds the startup project and asks it for the context. `Program.cs` is currently a
bare host that registers nothing, so EF has no way to construct `AssistantDbContext` and will
fail with *"Unable to create a DbContext of type 'AssistantDbContext'"*. This is not optional
plumbing — without it Step 5 cannot run.

Add `src/Assistant.Repository/AssistantDbContextFactory.cs`, internal sealed, implementing
`IDesignTimeDbContextFactory<AssistantDbContext>`. It builds options with `UseNpgsql` against the
compose connection string, and is used **only** by the EF tooling — never at runtime.

The alternative, registering the repository in `Program.cs` now, drags configuration binding and
a connection string into `Worker` before anything needs them. F14 wires the host properly; the
factory keeps that deferred and keeps the concern inside `Repository`.

- [ ] **Step 5: Generate the migration**

```bash
dotnet ef migrations add InitialCreate \
  --project src/Assistant.Repository \
  --startup-project src/Assistant.Worker
```

- [ ] **Step 6: Read the generated SQL before trusting it**

Run: `dotnet ef migrations script --project src/Assistant.Repository --startup-project src/Assistant.Worker`

Confirm in the output: exactly 7 columns; `status <> 0` and the sent-requires-due constraint
present; **no** `completed_at`, **no** index, **no** other tables. Paste the SQL into the report.

- [ ] **Step 7: Build** — `dotnet build`, 0 warnings.

- [ ] **Step 8: Commit** — `feat: add the reminder_tasks schema and its first migration`

### Task 3: The test harness

**Files:** create `tests/Assistant.IntegrationTests/Infrastructure/PostgresFixture.cs`.

- [ ] **Step 1: Write `PostgresFixture`**

```csharp
public sealed class PostgresFixture : IAsyncLifetime
{
    private const string DefaultConnectionString =
        "Host=localhost;Port=55432;Database=assistant_test;Username=assistant;Password=assistant;Include Error Detail=true";

    private Respawner? _respawner;

    public string ConnectionString { get; } =
        Environment.GetEnvironmentVariable("ASSISTANT_TEST_DB") ?? DefaultConnectionString;

    public async Task InitializeAsync() { ... }   // see below
    public async Task ResetAsync() { ... }
    public Task DisposeAsync() => Task.CompletedTask;
}

[CollectionDefinition(Name)]
public sealed class PostgresCollection : ICollectionFixture<PostgresFixture>
{
    public const string Name = "postgres";
}
```

**Complete reference implementation:** `docs/2026-08-16-personal-ai-assistant-slice1-plan.md`,
Task 3 Step 8, has this fixture written out in full. Copy it, with two changes: it calls
`provider.MigrateAssistantDatabaseAsync()`, which matches what Task 2 Step 3 builds here, and it
predates the YAGNI reset so it needs no other adjustment.

`InitializeAsync` must: poll the connection until it opens, with a bounded 60s deadline, then
build a provider, call `MigrateAssistantDatabaseAsync`, then create the `Respawner` with
`DbAdapter.Postgres`, schema `public`, ignoring `__EFMigrationsHistory`.

`Include Error Detail=true` is worth keeping for debugging — it puts parameter values into error
messages. It is **not** what populates `PostgresException.ConstraintName`; PostgreSQL sends the
constraint name in the error's own fields regardless. Task 4's assertions do not depend on it.

The readiness poll is not optional. `docker compose up -d` returns before Postgres accepts
connections, and that gap is the most common cause of a flaky first test.

- [ ] **Step 2: Build** — `dotnet build`, 0 warnings.

- [ ] **Step 3: Commit** — `test: add the Postgres integration fixture`

### Task 4: Prove the schema and its constraints

**Files:** create `tests/Assistant.IntegrationTests/Schema/ReminderTaskSchemaTests.cs`.

Tests use **raw SQL**, deliberately. F1 has no repository, and the point of these tests is to
write rows the mapping would never produce. Raw SQL is the right tool for exactly this case.

- [ ] **Step 1: Write the failing tests**

Class summary: `/// <summary>` newline `/// Test class for the <c>reminder_tasks</c> schema.`
newline `/// </summary>`. Gherkin summary on each test, `When`/`And`/`Then` on separate lines.
AAA with explicit comments. Names follow `Subject_Scenario_ExpectedResult`.

| Test | Asserts |
| :--- | :--- |
| `Migration_AppliedToEmptyDatabase_CreatesReminderTasksTable` | the table exists with exactly the 7 expected columns, queried from `information_schema.columns` |
| `Insert_StatusUnknown_ViolatesStatusKnownConstraint` | raw insert with `status = 0` throws, `ConstraintName == "ck_reminder_tasks_status_known"` |
| `Insert_ReminderSentWithoutDueTime_ViolatesSentRequiresDueConstraint` | raw insert with `reminder_sent_at` set and `due_at` NULL throws, `ConstraintName == "ck_reminder_tasks_sent_requires_due"` |

Constraint assertions pin the name, not a substring of a stack trace:

```csharp
var ex = await Assert.ThrowsAnyAsync<PostgresException>(Act);
Assert.Equal("ck_reminder_tasks_status_known", ex.ConstraintName);
```

The column test asserts the exact set, so adding a column later without updating this test
fails loudly — which is the point, given four columns are scheduled to return.

- [ ] **Step 2: Run them and watch them fail for the right reason**

```bash
docker compose -f compose.test.yaml up -d
dotnet test tests/Assistant.IntegrationTests
```

Before the migration exists they fail on a missing table. Record the failure output.
